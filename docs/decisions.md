# 決めたこと

このリポジトリを起こすまでに決めたことを、根拠つきで置く。
後から蒸留のループに載せるので、判断の型が読める形にしておく。

## 上流をもう追わない

`yohey-w/multi-agent-shogun` は 2026-08-06 を最後に止まっている。
直近 12 週の commit はほぼ 0。

止まっているだけではなく、作者が README で現状維持を宣言し、後継として `kagemusha` を案内している。

- 共通祖先: `v5.1.0` (2026-05-23)
- 乖離: 上流 16 commit / こちら 13 commit・58 files・+4161/-207

追いつく先が無いので、上流互換のために bash と YAML を守る理由も無い。

## 乗り換えない

kagemusha は作者が 10 体の軍勢を畳んだ結論を配っている。
その結論は採らない。

軍勢は成果を出している。
2026-08-24 の一日で、VRT の baseline 選定の欠陥を数字つきで突き止めた
(`58 - 23 = 35 = 30 + 5`。露出している PR も 6 本洗い出した)。
一人ではこの幅は出ない。

借りるのは判断の型であって、軍勢を畳むことではない。

## TS を主にする理由は、好みではなく失敗録

書き換えの動機は、実際に繰り返している失敗の形にある。

| 事象 | 型のある層なら |
|---|---|
| `queue/shogun_to_karo.yaml` が YAML として parse できない (cmd_668 から 703 が 2 字下げで入れ子) | 書き込みが schema を通るので起こらない |
| 採番を誤り、既存の cmd を上書きしかけた | id の重複が弾かれる |
| `git show HEAD:` が空を返し、空文字列を parse して「妥当」と判定した | 空は空として落ちる |
| `cmd \| tail -1 && echo OK` による偽の緑 | 例外か戻り値で判定する |
| `inbox_write.sh` の本文が Python ソースへ直接展開され、`\n` が実改行に化ける | 文字列を組み立てない |
| watcher の二重起動 | — |

grep で読める限り、壊れていても誰も気づかない。
それが今の造りの本質になる。

## Rust は最初は入れない

一つ目の言語がまだ何も証明していないうちに二つ目を足すのは、根拠の無い費用になる。

watcher は IO 待ちなので、速さが効く場所でもない。

入れるとしたら理由は一つだけ。
監視役は他のすべてが壊れたときに生きていなければならないので、依存の無い一枚のバイナリにしたい、という場合。
その壊れ方を実際に見てから決める。

### 訂正 (2026-08-26)：測る軸を誤っていた

「速さが効く場所でもない」は正しい。誤っていたのは、**速さで測ろうとしたこと**。
常駐する側の費用は速さではなく、何も起きていない間の居座りである。

現行 `scripts/inbox_watcher.sh` の実測：

| | 現行 (bash) | 芯 1 本 (Rust) |
|---|---|---|
| プロセス数 | 20 | 1 |
| RSS 合計 | 61.8 MiB | 3.6 MiB |
| 何も起きぬ 60 秒の起動回数 | 72 | 0 |

内訳は inotifywait 29 / python3 22 / bash 21。`inotifywait -t 30` で
30 秒ごとに起動し直し、未読を数えるたびに python3 が PyYAML を読み込む。
一日に直せば約 10 万回。何もしていない間の話である。

殿の要件も同じ軸だった——「watcher は常時動く故、低メモリを要件とする」。

道具立ては既にあった (cargo 1.96.0 / g++ 15.2)。新たに入れたものは無い。

## kagemusha は submodule で pin する

fork しない。
kagemusha は今も動いている (2026-07-26 作成・2026-08-22 push) ので、fork は分岐の管理を増やすだけになる。

### submodule を汚さない

`config.env` は既定で kit の中に置く造りだが、`LOOP_CONFIG` で外に出す。
状態はすべて `PROJECT_ROOT` の外へ出る造りなので、これで submodule は無変更のまま保てる。

### ファイル名を直書きしない

`manifests/scaffold.tsv` が写しの一覧をデータとして持っている。
こちらの scripts は個々のファイル名を直書きせず、この tsv を正として突き合わせる。

pin を上げたときに、壊れではなく diff として現れるようにするため。

## 正本を 3 つにしない

いま `memory/MEMORY.md` と `memory/*.md` (60 本)、加えて CLI 側の自動記憶がある。
そこへ kagemusha の薄い正本を素で足すと、正本が 3 つになる。

対応を先に決める。

- kagemusha の L1 (薄い正本) → 既存の `memory/*.md` の feedback 群へ写す
- L2 (追記専用台帳) → 新設する
- 並び立つ正本は作らない

## 権限を飛ばす旗は既定にしない

kagemusha の `config.env.example` は `AGENT_FLAGS="--dangerously-skip-permissions"` を既定にしている。

作者自身、蒸留の便にだけはこれを流さない造りにしていて、理由も書いている。

> プロンプトの中の文字列を、プロンプトの中の文字列で止めることはできない。

こちらの禁止事項 (D001 から D011) は prompt 層の縛りなので、この旗が付いた無人の便はその縛りが効かない場所を走る。

便ごとに必要な道具だけを `--allowedTools` で挙げる。

## 配送は工程として持つ

kagemusha が最も強く警めているのがこれになる。

> 書き出しは保管であって、配送ではない。
> 門は設計どおり存在していて、門に候補が到達していない。

kagemusha 側には配送路そのものが無い。
こちらには `dashboard.md` の要対応欄がある。

審査キューの行き先はそこにする。

## 配達層を書き直すときに持ち込む要件

shogun の `scripts/inbox_watcher.sh` を読んで見つけた欠陥。
bash 側は直さず、honden で配達層を書くときに構造として解く。

### CLI の識別は閉じた集合で、外れたら黙って置き換えない

`is_valid_cli_type` の一覧に `cursor` が無い。

```
claude|codex|copilot|kimi|opencode) return 0 ;;
*) return 1 ;;
```

そして未知のときは `codex` を返す (fail-closed のつもりの既定)。
結果、ログにこう出続ける。31 秒ごとに、cursor を使う 3 体ぶん。

```
[WARN] CLI unresolved for ashigaru7 (pane='cursor', arg='cursor'). Fallback=codex-safe.
```

pane も引数も `cursor` と明言しているのに弾かれ、別物に化ける。

**置き換えが起こすのは、正しく書かれた経路の死。** watcher には cursor 専用の
分岐が 5 箇所ある (リセット命令 `/new-chat`、送信の作法、busy 判定の
`ctrl+c to stop`)。どれも `$effective_cli` を見ているので、`codex` が
渡る限り一度も通らない。**書かれていながら到達不能になる。**

honden では、識別できない CLI は**代替値を置かずに拒む**。
黙って別物として扱うより、止まって名指しするほうが安い。

### 既定への落下は、失敗を隠す

上と同じ話の一般形。「安全な既定へ倒す」は、倒した先が正しく動いてしまうと
気づけない。この件は `/new` が Cursor でエイリアスとして通るせいで、
リセットだけは偶然成功していた。だから「時々おかしい」に留まり、
完全には壊れず、長く見つからなかった。

**部分的に動く fallback がいちばん見つけにくい。**

### 変わる値を鍵にした抑制は、負荷が高いほど効かない

```
if [ "${LAST_NUDGE_COUNT:-}" = "$unread_count" ] && … # 件数が同じ時だけ抑える
```

件数が変われば冷却を無視して即座に打つ。だが件数は、報せが来るたび変わる。
家老は足軽 7 体 + 軍師 + 将軍から受けるので常に動く。**抑制が一度も効かない。**

honden の抑制には、値と無関係な最短間隔を必ず置く。

### busy 判定は CLI ごとに試験を持つ

`lib/agent_status.sh` は CLI ごとに別の文字列を探す。Cursor は
`ctrl+c to stop`、Claude は `esc to interrupt`。

だが cursor の busy/idle を確かめる試験が 1 本も無い。文字列の出どころは
書いた人の観測だけになっている。画面の文字は CLI の更新で変わるので、
試験で固定していないものは黙って腐る。

honden では、判定に使う文字列は必ず試験の固定値として持つ。

### nudge の合図は、agent 番号と衝突している

`inboxN` の N は未読数。だが足軽の番号も 1〜7 で、同じ範囲になる。
`inbox3` は「未読 3 件」とも「足軽 3 号」とも読める。実際に読み違えが出ている。

honden は type を 5 種に締めてあるので、開く前に分類まで出せる。

```
未読3 cmd1 報告2
```

これで「いま手を止めるべきか」が読む前に判ずる。`clear_command` が
混じっているときは、特に。いまは全ての合図が等しく緊急で、足軽は必ず
手を止めて読むしかない。

### /clear を配達の手段にしない

いまの梯子は 4 分で `/clear` を送る。これは「合図が届かないかもしれない」
という前提から来ている。届かないなら、セッションごと作り直して YAML を
読み直させるしかない。

多くの CLI は実行中に打った入力を捨てず、区切りで受け取る。届くなら
`/clear` は要らない。**配達のために文脈を焼くのは割に合わない。**

ただし「どの CLI が積むか」は未測定。測ってから梯子を変えること。
「積まれるはず」で抑制を外し、実は捨てられていたら報せが黙って消える。

## 先例: `.opencode/tools/mark-as-read.ts`

OpenCode だけは、既に直書きをやめていた。read フラグを立てるのに汎用の Edit を
使わず、専用の道具を通す造りになっている。honden が向かっている方向と同じ。

取るべきものが 4 つある。

### 名乗りは環境から取る

```ts
function assertCurrentAgent(targetAgentId: string): void {
  const currentAgentId = process.env.OPENCODE_AGENT_ID?.trim();
  if (currentAgentId !== targetAgentId) {
    throw new Error(`Refusing to mark another agent's inbox as read: …`);
  }
}
```

**名乗りを引数に任せると、名乗りが検査にならない。**

honden の `inbox write` は当初 `from` を自己申告のまま受けていた。布陣の外からの
騙りは止めていたが、中では足軽3号が karo を名乗れた。この先例に倣って
`HONDEN_AGENT_ID` (無ければ pane の `@agent_id`) と突き合わせる形に直した。

布陣の中に居るのに誰か分からないときは書かせない。「たぶん本人だろう」で
通すと検査が消える。

### 重複は取らずに落とす

同じ id が 2 つあれば、最初のものを取るのではなく落とす。read 欄が 2 つ
あるときも同じ。cmd_668 の二重採番と同じ型の危険を、正しく扱っている。

### 済んでいるものは、成功として返す

既に `read: true` なら `changed: false` で返す。エラーにしない。
何度呼んでも同じ結果になる。

### 行を差し替えるだけで、書き直さない

```ts
lines[targetBlock.readLine] = "  read: true";
```

YAML を読み直して書き戻すのではなく、その 1 行だけを置き換える。だから
書式もコメントも壊れない。`shogun_to_karo.yaml` を壊した経路を踏まない。

### honden では要らなくなるもの

同じファイルにある atomic write (temp + rename)、mkdir によるプロセス間ロック、
50 回のリトライは、SQLite の取引が代わりに担う。

だが**なぜそれらが要ったのか**は残る。ファイルを正本にする限り、原子性も
排他も自分で組むしかない。組めば、組んだものの正しさを誰かが確かめねばならない。

## 合図は日本語で書かない

`inbox_notice unread=3 report_received=2 cmd_new=1 urgent=1`

受け取るのは人ではなく、各 CLI の裏に居るモデルになる。claude / codex /
cursor / opencode / copilot / kimi と種類があり、日本語の記号 (★ など) や
語の切れ目の扱いはモデルごとに揺れる。

key=value の羅列なら、どのモデルでも同じに読める。type の名はもともとこの系の
識別子で ASCII なので、そのまま使える。

先頭を `inbox_notice` にしたのは、`inbox3` の 3 が未読数なのに足軽の番号も
1〜7 で同じ範囲になり、「足軽 3 号」と読み違える事例が実際に出ているため。
数を key=value へ移せば衝突しようがない。

`urgent` は 1 か 0。cmd 系と clear_command が混じっているときだけ 1 になる。
これで「いま手を止めるべきか」が開く前に判ずる。

## 迂回は名のある一本にする

家老が倒れれば誰も振れなくなる。指揮系統の縛りが、まさにその時に効いてしまう。
だから迂回の道は要る。だが名の無い抜け道は、いずれ常道になる。

四つを課した。

1. **明示** (`--bypass`)。誤って通れない
2. **理由が必須**。空も、短すぎるものも、長くても中身の無いもの (`ああああ…`) も弾く
3. **別の action として台帳に残す** (`task.assign.bypass`)。数えられるように
4. **迂回した時の相手の様子を併せて記録する**

```
shogun → ashigaru1  [task.assign.bypass]
  subtask_1_… cmd=cmd_1 reason="家老が沈黙して40分。仕事が止まっておる"
  [karo: status=不明 holder=なし lease_until=なし unread=0 last_activity=なし]
```

4 つ目が肝になる。後から「本当に家老は倒れていたか」を検められるし、
迂回が増えれば「常道が壊れている」という報せになる。回数そのものが指標になる。

迂回しても他の守りは効いたままにする。能力の足りない者へは振れないし、
上役へも振れないし、無い司令の下へも振れない。緩めるのは指揮系統の 1 点だけ。

## 貸与の強制解除も、同じ形にする

足軽が握ったまま倒れると、持ち主しか手放せない造りでは誰も解けない。
`expired()` は並べるだけで直さないので、詰まったままになる。

迂回と同じ四つを課した。

```
$ honden lease release ashigaru1
  ashigaru1 を握っておるのは ashigaru1 である。他人の持ち場は手放せぬ。
  倒れて詰まっておるなら --force --reason "…" で解ける。跡は台帳に残る。

$ honden lease release ashigaru1 --force --reason "足軽1号のpaneが落ちて1時間"
  ashigaru1 の持ち場を空けた（強制。台帳に跡が残る）
```

```
shogun → ashigaru1 [lease.release.force]
  task=subtask_1_… prev_holder=ashigaru1 解除時の状態=held
  lease_until=2026-08-25T15:54:28Z reason="足軽1号のpaneが落ちて1時間"
```

`解除時の状態=held` が肝になる。**まだ生きていた貸与を取り上げた**という事実が残る。
「倒れていたから解いた」と言われたときに、台帳が `held` と言っていれば食い違いが分かる。
倒れていたなら `expired` と残る。

断り文に道を書くのも同じ理由。隠せば、いずれ誰かが別の抜け道を掘る。

## 報告の路は現行のまま、受け渡しだけ変える

現行の路はこうなっている。

```
足軽 ──report_received──> 軍師 ──verdict──> 家老 ──dashboard──> 将軍
```

これを変える理由が無い。軍師が品質を検め、家老が交通整理をし、将軍が裁く
という分業は、instructions/*.md 全体がその形で書かれている。路を変えると
指示書を全部書き直すことになり、移行の間じゅう二重の作法が並走する。

変えたのは**宛先の渡し方**だけ。現行は

```bash
bash scripts/inbox_write.sh gunshi "足軽{N}号、任務完了でござる。" report_received ashigaru{N}
```

と、宛先を毎回書く。書ける以上、間違えられる。F001「将軍へ直に報せるな」が
禁止事項として書いてあるのは、書けてしまうからである。

`honden report submit` は宛先を取らない。撃つ先が引数に無いので、飛び越えようがない。
禁止事項を守る意志が要らなくなる。

同じ理由で `cmd done` は将軍の inbox を鳴らさない。現行 karo.md の
`to_shogun: false`（殿の入力を割り込みで潰さぬため）と同じ扱いで、
将軍へは dashboard を通す。

## 報告と合図を 1 つの取引にする

現行は 2 手順に分かれている。

1. `queue/reports/ashigaru{N}_report.yaml` を書く
2. `inbox_write.sh` で軍師を起こす

1 だけ済ませて 2 を忘れると、報告は在るのに誰も知らない状態になる。
これは検知されない。誰も待っていないので、待ちぼうけにすらならない。

`report submit` は両方を 1 つの取引で行う。報告が入れば必ず軍師の未読が増える。
どちらか一方だけが起きる筋を消した。

## 受け入れ条件は番号で引く

現行の足軽の報告には既に `acceptance_check:` が並んでいる。

```yaml
acceptance_check:
  - 試験掛け直しなし: 済（将軍実測 job 18 / service 195 / exit 0 を引用）
  - push していない: 済
```

材料は揃っている。足りないのは、この並びと cmd の `acceptance_criteria` を
突き合わせる所だった。突き合わせないので、条件を 1 つ書き落としても気づかない。

**文言では照合しない。番号で引く。** 写し間違い・言い換え・要約で
別物になった時、文言照合は「その条件は報告に無い」と言うか、
あるいは緩く一致させて「覆った」と言う。どちらも誤る。
番号なら、指している先が一つに決まる。

そのため `cmd_acceptance.idx` を 0 始まりから 1 始まりへ変えた。
人が読んで指す番号に「条件 0」は要らない。

## 「済」だけの証拠は通さない

`acceptance_check` の実データは「済（証拠）」の形と「済」だけの形が混在している。
後者は覆ったことの証にならない。後から検める者が辿れないからで、
「並べれば覆ったことになる」なら、門はあっても開きっぱなしになる。

`checkReason` と同じ考えで形だけの通過を弾く。
済 / 完了 / OK / done / pass / 〇 / ✓ 単独と、6 文字未満を返す。

殿の言葉で言えば「変な値で無理やり突破」も「仕事放棄」も、どちらも
丁寧に追い返す。追い返す時は条件の文言を添える——何を書けばよいか
分からないまま追い返すと、次も同じものが来る。

## blocked と failed は覆う義務を負わない

`done` だけが条件を覆う義務を負う。塞がれた仕事に証拠は出せない。
出させると嘘が書かれる。書かれた嘘は、覆ったことになって門を通る。

現行にも blocked の報告は実在する。その筋を潰さない。

## 検査を集めるだけで判定に結ばないのを弾く

軍師の QC には `checks:` が並ぶ。FAIL を含んだまま `verdict: APPROVED` と
書けてしまうと、検査を並べる意味が無い。

これは koyori-app/vrt PR#19 で三度繰り返した型と同じ——
`errors` に積むだけで判定に使わない。集めたことを対処したと取り違える。
ここでは FAIL が 1 件でもあれば APPROVED 系を弾き、どの検査が落ちたかを並べる。

## 残りは司令ぜんたいで数える

`report submit` の出力に「残り」を出すとき、自分が覆わなかった分を引くと、
他の足軽が既に覆った条件まで残りに出る。受け取った足軽は二度手間を踏む。

司令ぜんたいの覆い具合から引く。誰が覆ったかは `honden cmd show` に出る。

## 形を呼び出し側で見る欄を設ける

`validate` は既定で文字列を要求する。`acceptance` は対応でも並びでも
受けるので、既定のままでは正しく書かれた対応が
「文字列で書く項目」として弾かれる。

`structured: true` を足した。**形の検めをしないのではなく、
検める場所を呼び出し側へ移す**。`normalizeAcceptance` と `checkEvidence` が
番号の範囲・証拠の実質まで見るので、緩くなってはいない。

同じ理由で `report_id` も `structured` にした。YAML に `report_id: 12` と
書けば数で入り、旗で渡せば文字列で入る。どちらも通して、数かどうかは自分で見る。

## 仕事の番号に時刻だけを使わない

`subtask_${cmd}_${Date.now().toString(36)}` は、同じミリ秒に 2 件振ると
同じ番号になる。試験で実際に衝突し、inbox の主キー違反で
2 件目の割り当てが丸ごと落ちた。

時刻に短い雑音を足した。番号が衝突すると、割り当てが落ちるだけでなく、
落ちたことが「そんな仕事は無い」として後から現れる。

## 芯は agent も pane も未読も知らない

常駐する芯 (`core/watch`) が知っているのは 3 つだけ。

1. 何か書かれた（inotify が鳴った）
2. 落ち着くまで少し待つ（束ねて 1 回にする）
3. 手を呼ぶ。手が「次はいつ起こせ」と言うので、それまで寝る

未読の数え方も、合図の文面も、escalation の段も、全部 honden 側に置く。
芯へ持ち込むと、同じものに 2 つの実装が生まれる。**合図の形で一度やった**——
`inbox unread` と送信後の案内が別の文字列を返しており、指示書の記述と
ツールの出力が食い違っていた。二度は繰り返さない。

手との約束は一行だけ。手は最後の行に `{"next_wake_ms": N}` を出す。

読めなければ既定の網（`--fallback-ms`）へ落とす。**読めなかったことを
「今すぐ来い」と解さない。** 壊れた手が回転を生む。
念のため呼び出し間隔に下限 (`--floor-ms`) も置いた。

## 芯は依存を一つも持たない

常駐する側は、他のすべてが壊れた時にも生きていなければならない。
依存が増えるほど、壊れ方の筋が増える。

inotify は syscall を 3 つ呼ぶだけで足りるので、`extern "C"` で自前で宣言した
(`core/watch/src/sys.rs`)。unsafe はそのファイルだけに閉じてある。
crates.io から何も取らないので、供給網の問いも起きない。

判断の中身 (`src/lib.rs`) は syscall を持たないので、そのまま試験できる。
束ね・下限・既定の網・壊れた手——10 件とも実時計を使わずに検めている。

## 合図の口を正本から分ける

芯が見張るのは `<正本>.signal` という一点で、正本そのものではない。

理由は実測。見張り先へ書く手を置いたところ、**6 秒で 27 回まわった**
(2026-08-26)。手は正本を読み、届けたら台帳へ書く。正本を見張ると、
その書き込みで芯がまた手を呼び、手がまた書く。

下限 (`--floor-ms`) は回転の速さを抑えるだけで、止められない。
口を分ければ、その筋が構造として消える。合図の口へ触るのは
「誰かの未読が増えた時」だけで、手は決して触らない。

そのため inbox への挿入を `deliver()` 一本へ寄せた。4 か所に同じ INSERT が
散っていると、合図を出す所と出さぬ所が生まれ、**届いたのに誰も起きない**筋ができる。

合図は取引の外で上げる。取引が巻き戻っても touch は戻らないが、
余計な起床が 1 回起きるだけで害が無い。逆に取引の中へ入れて
「書けたのに合図が出ない」筋を作るほうが重い。

## nudge を飛ばすのは TS

殿の言：「nudge を実際に飛ばすのは何でもよいが、ts が整合するだろう」。

飛ばす側は正本を読み、未読を数え、合図の文面を作り、pane を引き、
CLI ごとの違い（Copilot/Kimi は Escape×2、Claude/Codex は素の nudge）を見る。
どれも既に honden 側にあるものばかりで、芯へ写せば二重になる。

飛ばす側が常駐しないので、重さも問題にならない。何も起きていない間は
1 本も走っていない。

## 代役には実物の約束を守らせる（OOM 事故 2026-08-26）

偽の OAL (`oal::fake`) を書いた日に、試験が **25 GiB 食って OOM に殺された**。

```
Out of memory: Killed process 13721 (honden_watch-d5)
  total-vm: 34,049,972 kB   anon-rss: 25,032,704 kB
```

二つの誤りが噛み合っていた。

1. 偽の `wait` は台本を使い切っても `false` を返し続けた
2. 偽の時計が「呼ばれた回数」で進み、待っても進まなかった

`Scheduler` は永久に `Wait` を返し、密なループが回り、
毎周 `waits.push` が積もった。CPU も張り付いた。

**実物の `wait` は頼まれた時間ぶん眠る。** 眠らぬ代役を置くと、上の層は
「待ったつもりで一瞬も進んでいない」世界で回る。束ねも歯止めも期限も、
全部その進みを前提にしている。代役が約束を破ると、上の層はそれを検知できない。

手当ては三重にした。

| 層 | 手当て |
|---|---|
| 約束 | `Watch::wait` の註に「timeout ぶん眠ること」を書いた。移植先が最初に読む所 |
| 代役 | 台本を使い切ったら `Err` を返す。黙って「何も来ない」にしない。眠ったぶんだけ時を進める |
| 芯 | 待っても時が進まぬ回が続いたら誤りで止める (`SPIN_LIMIT`) |

三つ目は網であって約束の代わりではない。だが**止めるより回り続けるほうが良い場面が無い**。
誰も起こせぬ芯は生きている意味が無いので、誤りとして落として気づかせる。

歯止めが効いていることは、限界値を 64 にして待ちの回数がちょうど 64 で
止まることを見て確かめた。**外して確かめる陽性対照は、この件では踏めない**——
外せば機械が焼ける。限界値を動かして追随を見るのが、この型の代わりになる。

## 試験は必ず時間と記憶に縛りをかけて走らせる

上の事故は、試験がそのまま常駐して機械を食い潰したもの。

```bash
(ulimit -v 2097152; timeout 180 cargo test --offline)
```

`timeout` が回り続けを止め、`ulimit -v` が積もりを止める。
どちらも「焼けても機械は無事」にするためのもので、正しさの検めではない。

## ペインは名簿へ持たせず tmux から引く

出所は `@agent_id` である。設定ファイルへ書き写すと、ペインを組み替えた時に
静かに古くなる。古い対応で合図を撃つと **別人のペインへ打ち込む**。

現行で一度起きている
(multi-agent-shogun `incident_watcher_pane_misroute_2026_06_19`:
settings.yaml の gunshi の順ズレで pane+1 へ誤射)。

`@agent_id` は出陣時に付けられ、以後変わらない。動くのはペインの番号のほうなので、
番号ではなく名で引く。現行の karo.md も同じ引き方をしている
(`agent_id_lookup`)。撃つ時も番号ではなく `%4` のような識別子を使う。

一覧は 1 回で引く。1 体ずつ `tmux display-message` を呼ぶと頭数ぶん起きる。

## 将軍へ撃つかは、殿が在席かで決まる

### 訂正: 「例外」ではない（殿下知 2026-08-26）

当初これを旗 (`--wake-shogun`) にした。誤りである。
旗にすると「例外的に起こす」と読めるが、**自律運用では起こすのが前提**であって
例外ではない。殿の下知——「夜間や仕事中の自律運用では shogun に送るのは前提となる」。

判断軸も取り違えていた。撃たぬのは将軍が特別だからではなく、
**殿がいま打ち込んでおる最中を潰す**ゆえである。殿が席を外しておられる間は
潰す入力が無い。ゆえに軸は「将軍かどうか」ではなく「殿が在席か」になる。

運用の様態 (`src/mode.ts`) にした。

| | attended（既定） | autonomous |
|---|---|---|
| 将軍への合図 | 撃たぬ | 撃つ |
| 家老 → 将軍の inbox | 開かぬ（dashboard を通す） | 開く |

既定は attended。何も決めておらぬなら、潰さぬほうを採る。

### 撃つ側と書く側を同じ様態で判ずる

現行 karo.md の `to_shogun: false` は書く側の決め。撃つ側にも同じ守りが要る——
将軍の未読はほかの筋でも増えうるゆえ。だが**片方だけ開くと壊れる**。
書けるのに誰も起きぬ、あるいは書けぬのに起こす路だけ開く。

同じ関数 (`isAutonomous`) を両方から呼ぶ。

### 期限を切れる

様態を戻し忘れると、朝になって殿が打ち込んでおる最中に合図が飛ぶ。
**戻し忘れの害が、まさにこの守りが防ごうとしているもの**である。
自分で戻れるようにした。`--until 08:00` は、夜に書けば翌朝を指す。

期限なしの自律も通すが、断りを添える。断って通さぬと、
急ぎの時に迂回されて、迂回のほうが常道になる。

## 決めるところと撃つところを分ける

`plan()` は何も撃たない。`send()` が撃つ。

分けておくと `--dry-run` が「撃たぬ経路」ではなく「同じ経路の途中まで」になる。
別経路にすると、試した形と本番の形が違ってしまい、試した意味が薄れる。

ペインの一覧も差し替えられるようにした。試験が tmux の在り様に左右されると、
布陣が動くたびに赤くなる。赤が信用できなくなるほうが高くつく。

## 覚えは片付いたら消す

未読が 0 になった者の `since` を消さないと、次に未読が来た時に前の続きから
数え始め、**いきなり段 3（文脈消し）から始まる**。仕掛かりをいきなり捨てさせる。

消すのは `honden nudge` の入口で、段を数える前に行う。

## 一回きりの明示は、様態とは別に置く（殿下知 2026-08-26）

`--wake-shogun` を様態へ畳んだのは行き過ぎだった。殿の下知——
「明示的な指示があったとき用に --wake-shogun もあるべき」。

二つは別のものである。

| | 様態 (`honden mode`) | 一回きり (`--wake-shogun`) |
|---|---|---|
| 効く長さ | 戻すか期限が切れるまで | その一回だけ |
| 正本 | 動かす | 動かさない |
| 台帳 | `mode.autonomous` | `nudge.wake_shogun` |
| 使う時 | 殿が席を外される（夜間・仕事中） | 「いまこの件だけ起こせ」 |

一件のために様態を切り替えると、**戻し忘れが常態化する**。
一件のために自律へ移し、そのまま殿が席へ戻られる。
守ろうとしたものを、守るための操作そのもので壊す。

台帳の名を分けるのは、後から「なぜ殿の在席中に将軍が起こされたか」を
辿るため。`nudge.L1` に混ぜると、常道と明示が見分けられなくなる。

自律運用では印をつけない。そちらは常道であって、明示ではないゆえ。

### 理由は要るが、断りはしない

迂回の四箇条（明示・理由必須・別の action・相手の様子）のうち、
**理由必須だけを課さない**。ここだけ他と違う扱いにする根拠は、及ぶ範囲の差にある。

貸与の強制解除や家老の迂回は、他人の仕掛かりを奪う。
こちらは将軍のペインへ一度打ち込むだけで、しかも**殿自身が明示した時にしか使わない**。
理由を必須にすると、急ぎの一件で迂回され、迂回のほうが常道になる。

`--reason` は受けて台帳へ残す。書かれていれば辿れる。

## 様態を切り替えられるのは将軍だけ

様態が言い表しているのは「殿が席におられるか」という**布陣の外の事実**であって、
布陣の都合ではない。それを見ているのは将軍だけである。

誰でも切り替えられると、足軽が自分の合図を通したくて自律へ移せる。
移せば家老から将軍への路も開くので、**一体の都合で布陣ぜんたいの決めが動く**。
指揮系統を型で守っているのと同じ理由で絞る。

読むのは誰でもよい。合図を撃つ側が毎回読むゆえ、絞ると回らない。

弾く時は次の手を示す——「合図が通らぬなら、まず未読を片付けられよ」。
示さぬと、塞がれた側が勝手な道を探す。

### 残る穴

将軍のペインが死んでいると、誰も自律へ移せない。殿が席を外される前に
移しておくのが常道で、`--until` があるので戻し忘れは起きない。

`HONDEN_AGENT_ID=shogun` を置けば布陣の外からでも切り替えられる。塞いでいない。
inbox の名乗りと違い、これは**報せの差出人を騙る**話ではなく、
殿が直に操作する筋であり、台帳に actor が残る。
騙りを塞ぐべきは「誰からの報せか」を受け取る側が判ずる所であって、ここではない。

## 場所の重なりを調整する路（殿下問 2026-08-26）

殿の問い——「足軽の作業範囲、場所がダブルブッキングした時に調整するルートは？」

**路は無かった。** しかも現行の決めは、構造上守れない。

```
instructions/ashigaru.md:168       他の足軽のファイルを絶対に読むな
instructions/ashigaru.md RACE-001  衝突の恐れがあれば blocked にして家老へ伺え
instructions/karo.md   RACE-001    同じファイルへ複数の足軽を振るな
```

足軽は他人の持ち場を読めないので、恐れに気づけない。**気づけと命じながら、
気づく手立てを禁じている。** 見えるのは家老だけで、その拠り所は記憶しかない。

実際に破れた。本セッションで worktree を重ね、merge commit を生んだ (2026-08-25)。
将軍は cmd_709 に手書きで「vrt-fix32 は cmd_708 の足軽が持っておる。触るな」と
書いている——記憶が拠り所であることの証拠そのものである。

### 貸与とは別のものが要る

貸与 (`task.holder`) が答えるのは「その足軽が塞がっておるか」。
足軽 2 号が空いていても、足軽 1 号の木へ振ってはならない。
貸与だけではその振り分けが通る。

### 二つ置いた

1. **振る時に検める**。家老の記憶に頼らない
2. **足軽が自分で問える** (`honden claim check`)。他人の持ち場を読まずに
   重なりの有無だけ分かるので、守れなかった決めが守れる形になる

### 断る時は路を示す

「使えぬ」だけでは、塞がれた側が勝手な道を探す。
誰が・いつから握っておるかと、取りうる三つの手（待つ / 別を切る / 譲らせる）を並べる。
三つ目は相手の仕掛かりを止めるので、貸与の強制解除と同じ四箇条を課す。

### 重なりは前置きまで見る

`.worktrees/x` を握る者が居れば `.worktrees/x/apps` も重なる。同じ木の中だからで、
文字列が違えば別物としてしまうと、一段深い所から入れてしまう。
区切りの境目で切るので `.worktrees/xyz` は重ならない。

### 検めと取り置きを別に書かない

最初、振る前の検めと取引の中の取り置きを別々に書いた。
**外しても試験が赤にならなかった**——同じことを二度していたので、
片方を消してももう片方が拾う。

二つの経路があると、片方だけ直る筋ができる。取引の中の一本にした。

同じ型で、`force` の門も緑のままだった。理由の門が先に拾っていたので、
`force` を外しても落ちない。**理由はあるが force が無い**入力で試験を足した。
門の手前に別の門があると、奥の門は試されない。

## 読むのは開き、実行は塞ぐ（殿下知 2026-08-26）

殿の下知——「フラグを付けて何をしているか理解させた上で他足軽のタスクを
見れるべきかもしれない。claude code 本体でもモデルのお行儀がよければできる故」。

現行 `instructions/ashigaru.md:168` は「他の足軽のファイルを絶対に読むな」。
出所は cmd_020 の事故——足軽5号が足軽2号の仕事を**実行した**。

**禁じられたのは「読む」で、事故は「実行した」である。** 一緒くたにしたので、
衝突に気づくために読むという正しい筋まで塞がった。同じ指示書が
「衝突の恐れがあれば伺え」と命じているのに、気づく手立てが無い。

honden では分ける。

| | |
|---|---|
| 読む | 旗と理由を添えれば通る。台帳に `task.peek` として残る |
| 実行する | 通らない。報告は自分が握る仕事のものしか書けず、振れるのは家老だけ |

**実行の側が型で塞がっている以上、読むのを塞ぐ必要はない。**
散文の禁止で守っていたものを、型の禁止へ移した結果、
散文のほうを緩められるようになった。

理由を書かせるのは読ませぬためではなく、後から
「読んだだけか、手を出したか」を検められるようにするため。
覗いた出力には境目を書く——「手を出してはならぬ。調整が要るなら家老へ回されよ」。

## 衝突した後に、何が起きたのか辿る

worktree を分けても、枝が同じになれば衝突する。**detached HEAD で切れば
枝の取り置きすら立たない**——実際、現行の `.worktrees/vrt-cmd707` と
`vrt-cmd709` は detached である。

取り置きは起きる前に止める仕掛けで、起きてしまった後の路ではない。
`honden history` を別に置いた。

**解かれた取り置きも出す。** 衝突は往々にして「先に居た者が納めた後」に
分かるので、いま握っている者だけ見ても経緯が分からない。
台帳は追記専用ゆえ、譲らせた跡 (`claim.release.force`) も残っている。

取り置きが無い時は、**無いことを証拠にするなと断る**。
`--workspace` を書かずに振れば取り置きは立たない。
黙って「誰も触っておらぬ」と出すと、いちばん危うい筋——
宣言せずに触っている者——を見落とす。

## 語を差し替えられるようにする

`checkReason` の断りは「迂回には理由が要る」で始まっていた。
覗くのは迂回ではない。**迂回でないものを迂回と呼ぶと、読む者が身構え方を誤る**。
何のための理由かを言う語を渡せるようにした。

## 覗いたら家老へ報せる（殿下問 2026-08-26）

殿の問い——「家老に見たものがいること通知する？」。**報せる。**

覗いた跡は台帳に残るが、**台帳は誰も読まない**。積むだけで判定に使わねば、
集めたことを対処したと取り違える——この一連で何度も戒めてきた型そのもの。
調整できるのは家老だけなので、家老が知らねば調整は始まらない。

覗いた者に「家老へ回せ」と促すだけでは足りない。それは
「気づいた者が動くかどうか」に委ねることで、現行と同じ形に戻る。

### はじめ「重なった時だけ報せる」としたのは的を外していた

騒がしくせぬため、取り置きが実際に重なった時だけ報せる造りにした。**動かなかった。**

**取り置きが重なる状態は、振る門がそもそも作らせない。**
`take` も `assignTask` も重なりを弾くので、生きた取り置きが重なることはない。
条件にしたつもりのものが、常に偽であった。

危ういのは宣言されなかった側——`--branch` を書かずに振った、
detached HEAD で切った——で、そこには比べる取り置きが無い。
**重なりの有無を条件にすると、いちばん危うい筋でちょうど黙る。**

覗いたこと自体を報せる形へ変えた。足軽は遊びで覗かない。
理由を必須にしてあるので、覗きには必ず「なぜ」が付いている。
それがそのまま家老への報せになる。

騒がしさは、同じ相手の同じ仕事について二度報せないことで抑える。
相手が次の仕事へ移れば改めて報せる。

### 到達不能な検めを、消さずに試験する

`overlapBetween` は、正しく回っている限り常に空を返す。
だが消さない。**返したなら門を通らずに取り置きが入ったということ**で、
上流が壊れている印になる。

試験は正本へ直に行を入れて作る。通常の筋では作れない状態を、
試験だけが作れる形にしてある。「万一入ってしまった時に黙って通り過ぎぬこと」を
検めておるのであって、通常の筋を検めておるのではない——註にそう書いた。

### 陽性対照が届かなかった二つ

`signal` を外しても試験が緑のままだった。二度直している。

一度目は `:memory:` の正本を使っており、合図の口がそもそも無かった。
二度目は実体の正本にしたが、**振った時点で既に合図が上がっており**、
「前の合図がまだそこにある」だけで通っていた。
覗く前に合図の口を消してから検める形にして、ようやく赤になった。

前の状態が残っていると、後の操作を検めたことにならない。

## 場所を書かずに振ったら、所在から補う（殿下知 2026-08-26）

殿の下知——「無ければ現行の project の所在登録を継承してそこから補完、
無いなら無いでいい」。

### 約束と見立てを分ける

補った値は**見立て**であって約束ではない。

| | declared（明示） | inferred（見立て） |
|---|---|---|
| 重なった時 | 断る | 断らない |
| 見え方 | 出る | 出る。「見立て」と付く |

見立てを約束と同じに扱うと、**誰も約束していない場所で仕事を断る**。
現行は一つの案件へ複数の足軽を振るのが常なので、案件の根を握らせて断れば
その常道が止まる。見立ては「そこに誰が居るか」を見えるようにするためだけに置く。

### `path` をそのまま補ってはならぬ

所在登録には罠がある。`work_location: coder` の案件は `path` (WSL) が
参照専用で、実体は Coder の中。素直に `path` を補うと**押せぬ場所を握らせる**。

現行でも足軽が二度これで失敗している (cmd_266, cmd_273 — WSL で作業して push 403)。
`projects.yaml` にその戒めが長い註として書いてあるのに、
註は読まれる保証が無い。読まねば効かぬものを、読まずとも効く形へ移した。

休眠中 (`status: standby`) の案件も補わない。平時に使ってはならぬ枠ゆえ。

### 門が二重になり、また片方が試されていなかった

`if (source === 'declared')` と `conflicts(..., declaredOnly)` の二つがあり、
片方を外しても試験が緑のままだった。だが**今度は両方が要る**。

  門① 見立てを取る時、そもそも検めを通さない
      —— 無いと、案件の根が誰かの約束を含んでおる時に、
         場所を書かずに振っただけで振れなくなる
  門② 約束を取る時、見立てを重なりに数えない
      —— 無いと、見立てが約束を断る

同じ「見立ては断らない」を、二つの向きから守っている。
向きごとに試験を分けて、それぞれ赤になることを確かめた。

前は重複だったが今度は違う——**外して赤くなるかを見なければ、
どちらであるか分からない。**

## kagemusha の初期統合は、読み返す側から繋ぐ

kagemusha は二つの機構を持つ。**承認の列**（内向きは自律・外向きは人の承認で止める）と
**判断の蒸留**（却下の理由を溜め、蒸留し、次の回に読み返させる）。

初期統合として繋いだのは後者、それも**読み返す側の半分**である。

理由は honden 自身の欠けにある。honden は既に理由を集めていた——
迂回にも、強制解除にも、覗きにも `--reason` を課し、全部台帳へ落としている。
**だが一度も読み返していなかった。** 集めるだけで判定に使わぬのは、
集めたことを対処したと取り違えること——この一連で何度も戒めてきた型が、
honden 自身に残っていた。

### 検出器ではなく生成側へ戻す

棚の README の言——「検出器に戻すと見つけるのが速くなるだけ。生成側に戻すと
最初から起きなくなる。前者は線形、後者が複利」。

honden での生成側は、足軽へ渡す仕事そのもの。ゆえに `task assign` の時点で差し込む。
報告を検める軍師へ差し込んでも、線形にしかならない。

### 棚の決めをこちらで曲げない

kagemusha 側の造りには、それぞれ理由が書いてある。写す時に緩めなかった。

| 造り | 理由（kagemusha 側） | honden の扱い |
|---|---|---|
| `README.md` は棚ではない | 器の説明であって規約ではない | 読み飛ばす |
| `.example` が `.md` で終わらぬ | `*.md` で拾う仕組みが見本を「あなたの規約」として読み込まぬため | 拡張子を緩めない |
| 4 段すべてが棚に載る | 段が決めるのは「指示文に入れるか」だけ | 全部読み、選ぶ所で分ける |
| 規約は出典 8 件から | n=1 を法則にすると 1 本の癖が全成果物に転写される | 規約と常設だけ入れる |
| 出典の無い行は積まぬ | 後から誰も検算できない | 段が足りていても入れない |
| 棚は空で出荷される | 借り物の規約は自分で焼いた規約と同じ枠を食う | 空を異常として扱わない |

最後の一つが効いている。棚が空の間、この層は何も足さない。
**空の見出しだけを毎回付けると、読む側がその節ごと読み飛ばすようになる。**

### まだ繋いでいない半分

材料の側——honden の台帳を蒸留の材料として出す筋——は繋いでいない。
kagemusha の記帳の規律 2 が「verbatim（実発話）を残す。要約しない。
原則に昇格してよいのは quote が引けるものだけ」と定めており、
**honden の `--reason` は足軽や家老が書いた文であって、殿の実発話ではない**。

そのまま材料にすると、規律 3（推論は昇格させない）を破る筋ができる。
出すとしても `[working hypothesis]` 止まりで、昇格は人が行う——
その形にするなら別の増分として設計する。


## 外部レビューが見つけたもの（2026-08-26）

fable の副エージェントに批判的レビューを頼み、**中核経路に欠陥が並んでいた**。
指摘の重いものは全部こちらでも再現してから直した。

総評が正確だった——docs 自身が三度戒めた型が、中核経路にそのまま残っていた。

### ① 却下された報告の証拠で門が開いた

覆いを `verdict IS NULL AND status='done'` の報告すべてから数えていた。
軍師が REJECTED と判じても、**元の報告の verdict は NULL のまま**
（検めは別の行として入る）ゆえ、条件に外れなかった。

再現: 足軽1号が全条件を覆って done → 軍師 REJECTED → 足軽2号が些末な仕事で
条件1だけ覆って APPROVED → **cmd done が通った**。

仕様は「全条件が証拠つきで覆われ、かつ軍師が是」だが、実装は
「（却下済みを含む）誰かが証拠を並べ、かつどこかに是が 1 件」に弱まっていた。

覆いは、その証拠を出した報告そのものが是と検められていることを要る形にした。
併せて「証拠が出ておるか（claimed）」と「是と検められたか（covered）」を分けた——
納めた足軽へ残りを見せる時は前者を使う。検めを待っておるだけの条件を
「まだ誰も手を付けておらぬ」と出すと、次の者が同じ仕事をやり直す。

### ② 検査の門が、形の一つにしか置かれていなかった

`checks` を `Array.isArray` の中でしか検めていなかった。対応で書くと
（`checks: {lint: FAIL}`）**検査も保存も丸ごと素通り**し、FAIL 2 件を抱えた
APPROVED が通り、`report_check` は 0 行になる。

「集めるだけで判定に結ばぬ」を戒めた註のすぐ隣で、その門が片方の形にしか無かった。
二つの形を受け、**どちらでもない形は断る**ようにした。

### ③ 「自分の仕事を自分で是とできぬ」が足軽にしか成立していなかった

`submitQc` は名乗りが軍師かしか見ておらず、**対象が誰の仕事かを見ていなかった**。
軍師には仕事を振れる（`dispatch.ts`）ので、軍師が自分で報告を出し、自分で
APPROVED できた。検めの意味が消える所は、誰であっても同じである。

### ④ 貸与の寿命が両端で壊れていた

- `renew` がどこからも呼ばれておらず、**30 分を超える仕事は必ず期限切れ**になる
- 期限切れの持ち場へ**黙って上書き割当**でき、その瞬間
  **旧い仕事の報告が永久に出せなくなる**（報告は自分が握る仕事のものしか書けぬ）
- done / failed でも貸与が解けず、納めた足軽が次を振られなくなる

`lease.ts` の註は「期限切れは空きではない」と書いておったのに、
**振る側がそれを守っていなかった**。註は読まれる保証が無い。

期限切れは `--takeover --reason` を要る形にし、納めたら解き、
`honden lease renew` を繋いだ。

### ⑤ 文脈消しの冷まし中に連射になった

冷ましで段 3 が段 2 へ落ちる。その**落ちた段を覚える**と、次の回は経ちから
段 3 が出て「段が上がった」と判ぜられ、撃ち直しの間を素通りする。
Copilot の詰まった pane へ数秒間隔で Escape×2 + Ctrl-C が飛び続ける。

覚えるのは「escalation のどこまで来たか」であって「何を撃ったか」ではない。

### ⑥ 様態を切り替えた初弾が文脈消しになった

在席の間は将軍へ撃たぬが、**時計だけ回していた**。未読が 4 分を超えて滞留した
まま殿が席を外して様態を切り替えると、最初の一発が段 3 の `/clear`。
夜間運用の開始と同時に将軍の文脈が焼ける。

段が数えておるのは「撃ち始めてから返事が無い時間」であって、
「未読が置かれてからの時間」ではない。撃たぬ相手には時計を刻まない。

### ⑦ 影と実運用が同じ行を取り合っていた

「影は一方通行ゆえ安全」は doc 表には成り立つが、**task・report・inbox は
影と実運用が同じ行を取り合う**。honden で振った直後に shogun 側の YAML を
取り込むと task_id が差し替わり、足軽は報告を出せなくなる。

生きた持ち主が居る行は、影の側が譲る。

### ⑧ 衝突の報せが永久に黙った

台帳は追記専用ゆえ消えず、dedup の鍵に時刻が入っていなかった。同じ
(足軽, 相手, 場所) は**何日経っても二度と報されなかった**。註は
「相手が握り直せば at が変わるゆえ改めて報せる」と言っておったのに、
鍵にその at が入っていない。

半日の間だけ黙る形にした。`LIKE` もやめた——鍵に必ず含まれる `_` が
任意一文字に当たり、別の重なりを同じものとして黙らせる筋があった。

### ⑨⑪⑫ 散文のままだった禁止

- 取引の中の門が `force: true` で常時無効になっており、**実効は取引の外だけ**。
  見てから取るまでの隙が空いていた。門を取引の中の一本へ寄せた
- `--wake-shogun` に呼び出し主の検めが無く**誰でも将軍を起こせ**、
  しかも台帳の actor が `'nudge'` 固定で**誰が起こしたか跡が残らなかった**。
  様態を将軍に絞ったのに、同じ効果の一回きりが素通しでは絞った意味が無い
- 取り置き・貸与の強制解除は、案内文が「家老が」と言うておったのに、
  **どの名乗りでも通っていた**

### 元の probe は落ちようがなかった

レビューが残した再現試験は `console.log` で観測しており `expect` が無かった。
**集めるだけで判定に使わぬ型が、それを見つけるための道具に出ていた。**
正しい振る舞いを主張する形へ書き直し、直るまで赤にした。

### 二重の門は、また二度出た

「④a 期限切れを空きにせぬ」と「引き継ぎに理由が要る」が、外しても赤にならなかった。
どちらも手前の別の門が拾っていた。片方を消して一本にするか、
奥の門に届く試験を足すかで解いた。

**この型はこれで五度目である。** 門を足したら、外して赤くなるかを必ず見る。

## 名乗りの出所は pane。環境変数ではない（殿下問 2026-08-26）

殿の問い——「環境変数が優先なのは既存から引き継いでるのであれば経緯がある気がする」。
確かめた。**引き継ぎではなく、こちらが足したものだった。**

```
現行 scripts/session_start_hook.sh:22-30
  AGENT_ID=""
  if [ -n "${TMUX_PANE:-}" ]; then
      AGENT_ID=$(tmux display-message -t "$TMUX_PANE" -p '#{@agent_id}')
  fi
  if [ -z "$AGENT_ID" ]; then exit 0; fi    # 布陣の外として何もせぬ
```

現行に環境変数の名乗りは無い。**pane が唯一の出所**で、取れなければ
「布陣の外」として干渉しない。

`HONDEN_AGENT_ID` を足したのは、布陣の外から叩く筋（試験・素振り・外部セッション）で
誰かを名乗る要があったため。**それ自体は要る。** 誤っていたのは順序で、
環境変数を pane より先に見ておった——布陣の中でも env 一つで他人を名乗れた。
名乗りが検めにならない。

pane を先にした。環境変数が効くのは、pane が名を持たぬ時だけ。

### 食い違いは黙って解かない

pane が言う名と env が言う名が違うなら、**どちらかが誤っている**。
片方を静かに採ると、誤りが誤りのまま通る。pane を採るが、断りを出す。

```
※ 名乗りが食い違っておる。
  pane は karo と言い、HONDEN_AGENT_ID は ashigaru1 と言うておる。
  どちらかが誤っておる。pane を採るが、まず食い違いを正されよ。
```

### TMUX_PANE が空のとき pane を引かない

空のまま `tmux display-message -t ""` を打つと、tmux は**アクティブな pane の
`@agent_id`** を返す。2026-07-06 に実際に起きている——将軍が別陣営の pane を
自分と誤認し、その tty へ書き込んだ (memory: pane_identity_verification)。

「引いて空だった」と「引いてはならぬ」は違う。後者にした。

### 決め方は一箇所に置く

`inbox write` の中に同じ解決が別に書いてあった。片方だけ直る筋ができるので、
`src/identity.ts` へ寄せた。

## 芯は起きるたびに見張りを付け直す

**inotify の見張りは inode に付く。** 見張っておるファイルが消されて作り直されると、
新しい inode には何も付いておらず、以後は静かに黙る。既定の網（5 分）だけが残り、
合図が来ても即座には起きない。

合図の口は書き換えで作り直されうるので、この筋は実際に起きる。

`inotify_add_watch` は同じ inode へ付け直しても同じ番号を返すだけで、何度呼んでも
害が無い。ゆえに起きるたびに無条件で付け直す。**どの名が動いたかを見て分岐しない**——
見落とした名が黙って落ちる筋を作らぬため（`Watch::wait` の註と同じ考え）。

付け直しに失敗しても倒れない。芯が落ちると誰も起こせなくなる。次に起きた時にまた試す。

## 指揮系統を、宛先の検めとしても置く

`report submit` は宛先を取らぬので飛び越えようがない。だが **`inbox write` は
宛先を取る**。塞がねば、報告路の守りがこちらで迂回できる。

現行 `instructions/ashigaru.md` の F001（将軍へ直に報せるな）は散文のままで、
布陣の中なら足軽→将軍の直訴も、足軽→足軽の `clear_command`（他人のセッションを
消す）も通っていた。

| 禁じるもの | 代わりの路 |
|---|---|
| 足軽 → 将軍の直訴 | `honden report submit` |
| 足軽 → 足軽の差し向け | 家老へ回す。`honden peek` で検めれば家老へ自ずと報せが行く |
| 上役以外の `clear_command` | 家老へ回す。振り直すのが常道（Redo Protocol） |

**断る時は必ず代わりの路を示す。** 示さぬと、塞がれた側が勝手な道を探す。

布陣の外からの差出人は名簿に無く、指揮系統の中に居らぬので縛らない。
上下を当てはめようがないものに上下の決めを当てると、外からの正しい使い方が死ぬ。

## `ulimit -v` はリンカを縛る

`(ulimit -v 2097152; cargo test)` が `linking with cc failed` で落ちた。
コードの誤りではなく、**リンカが仮想メモリを要る**ためであった。

`bun test` には効くが `cargo test` の初回ビルドには効かない。
Rust 側は `timeout` だけで縛る——無限ループはそちらで止まる。

## 場所の同一は、土地を測って決める

`/mnt/c` (DrvFs) は**大小を区別しない**——`.worktrees/VRT-FIX32` で
`vrt-fix32` と同じ木が開く（実測 2026-08-26）。ext4 は区別する。

一律に畳むと、ext4 で本当に別の二つを同じものにする。
一律に畳まぬと、`/mnt/c` で**同じ木へ二人が入れる**。

ゆえに測る。実在する最も近い祖先の名の大小を入れ替え、同じ inode を指すかを見る。

### `/mnt/` で始まるかで決めない

この機では当て推量でも同じ答えが出る。だから当て推量でよい、とはならない——
case-sensitive を明示した DrvFs や、別の mount で誤る。

**そして、この機で同じ答えが出るということは、試験が両者を見分けられない
ということでもある。** 測り方を差し替えられるようにして、
「渡した土地の性質どおりに分かれるか」を検める形にした。
当て推量へ入れ替えると 2 件が落ちる。

### symlink は実在する時だけ辿る

これから切る worktree は実在しない。辿れぬことは異常ではない。

### 測れなければ畳まぬ側へ倒す

畳まぬ側は、多く断るだけで済む。畳む側へ倒すと、別物を同じものにする。

## 司令の書き換えを差分でも受ける（殿下問 2026-08-26）

殿の問い——「差分で書き換え出来るように diff -u 形式でも受け取る？」。受ける。

**丸ごと置き換えは、何が在ったかについて何も主張しない。** 長い本文を貼り直すとき、
気づかぬうちに一段落落としても誰も止めない。

差分は「いま何が書いてあるか」の主張である。当てれば主張ごと検められる。
文脈が合わねば当たらない——**思っていた中身と違う、と分かる**。

### 曖昧さは許さない。行番号のずれは許す

手で書いた差分は `@@` の数がずれる。そこで断ると使い物にならない。
行番号は目安として使い、合わねば文脈の塊を本文から探す。

だが**一箇所に定まる時だけ**当てる。見つからねば断り、二箇所以上でも断る。

`patch(1)` の fuzz のように文脈を削って当てにいくことはしない——
削った文脈の分だけ、誤った場所へ当たる余地が増える。
差分で受ける値打ちは「当たること」ではなく「**当たらぬ時に断ること**」にある。

### 後ろの hunk から当てる

前から当てると、行を増やした分だけ後ろの hunk の位置がずれる。
探しに行けば見つかることも多いが、同じ文脈が他所にもある本文では
曖昧として断られる——**正しい差分が、当てる順のせいで通らなくなる**。

### 外の道具を呼ばない

`patch(1)` はファイルを取る。ここで扱うのは正本の中の文字列である。
一時ファイルへ書き出して呼ぶと、失敗の筋（書き出し・権限・後始末）が増える。

### 差分の道と丸ごとの道を分けない

差分は当てた時点で文字列へ均し、以降は丸ごと渡された時と同じ道を通す。
二本持つと片方だけ直る筋ができる——この実装で五度踏んだ型である。

同じ欄を丸ごとと差分の両方で渡したら断る。どちらが効いたのか分からなくなる。

### 陽性対照が二度届かなかった

`後ろの hunk から当てる` と `宛先が無ければ断る` が、外しても赤にならなかった。

前者は、試験の hunk が行数を変えぬものだったので順序が観測できなかった。
行を増やす hunk と、同じ文脈が二箇所ある本文を組み合わせて、ようやく赤になった。

後者は、試験の入力が手前の門（`--- より先に @@ が来ておる`）で止まっていた。
`---` も `@@` も無いただの文章を渡して、ようやく届いた。

**門の手前に別の門があると、奥の門は試されない。** この型は六度目である。

## 差分をファイルにも効かせる（殿下知 2026-08-26）

殿の見立て——「t.replace の書き換えとそう遠くないことができるね」。そのとおりで、
**そして我らの道具のほうが緩かった。**

```python
assert a in t; t = t.replace(a, b)
```

`assert` は「a が在るか」を確かめる。だが `str.replace` は当てはまる所を
**全部**書き換える。「a が一つだけか」は誰も確かめていない。

この実装を書いておる間、将軍自身がその形で何十回も編集した。
害は出なかったが、**出なかったのは運であって、道具が守ったのではない。**

### 害が出ておらぬことは、二度しくじってから確かめた

一度目——「同じ 3 行の塊が二度出ておらぬか」を数えた。150 件出たが、
すべて `return {` や試験の定型。**代理指標がまた**（七度目）。

二度目——討ち直した検出器の陽性対照が「死んでおる」と出た。真因は
**仕込んだ註が長さの閾値（25 文字）に届いておらぬ**こと。検出器ではなく
対照の作りが誤っていた。危うく「検出器が壊れておる」と誤報するところだった。

対照が、こちらの閾値の粗さを暴いた。**対照を取る値打ちが、そのまま出た。**

最終的に見つかった重複は 1 件で、関数の説明と実装の傍註という意図した重複だった。

### 何を厳しくしたか

`honden patch` は文脈が**一意である時だけ**当てる。曖昧なら断る。
`patch(1)` の fuzz のように文脈を削って当てにいくこともしない。

複数ファイルは全部当ててから、まとめて書く。途中まで書いて止まると、
半端な状態がディスクに残る。

宛先が実在せぬなら断る。「空に対する差分」を許すと、
書き間違えた宛先が新しいファイルとして生まれる。
木の外（`../`）も断る——差分は人が手で書くもので、書き間違いも起きる。

### 道具が守っても、使わねば守られぬ

`honden patch` を作っても、将軍が `t.replace` を使い続ける限り効かない。
そこは道具ではなく規律の話である。せめて `t.count(a) === 1` を課す。


**本物の決裁が 16% しかない。** 本物が、片付いた物と覚え書きに溺れている。

散文には状態が無い。消すには「これはもう済んだか」を人が判断せねばならず、
判断には手間と責任が要る。だから誰も消さない。

**積むだけで判定に使わぬ型**が、ここにも出ている。この実装で何度も戒めてきた
ものが、我らの運用の中心にあった。

状態を持たせれば、絞り込みで消える。判断が要らない。

### 自由文は決裁の問いではない

「どうしましょう」では、殿が読んで、考えて、文で答え、受けた側がまた読んで解する。
**一語で再開できる形**にする。選択肢を 2 つ以上並べさせる。

現行の 🚨 は「無視したら何が起きるか」を言わない。だから積む側に痛みが無く、
積むだけ積まれる。止まるのか、既定へ倒れるのかを書かせる。

既定を置くなら期限も要る。**期限の無い既定は、いつまでも殿を待つか、
いつの間にか倒れるかのどちらかになる。** どちらも書いた者の意図ではない。

期限切れで既定へ倒れたものと、殿が決めたものを同じ `decided` にすると、

手で書き換える文書は、丈が伸びるほど当たり損ねる。節が二つに増えたのが
その証拠である。`decision` に状態が入れば、🚨要対応 の節は
**開いておるものを並べるだけ**になり、書き換えが要らなくなる。

### ① 影の取り込みが、実運用の報告を潰して門ごと落とす

`ingestReport` の重複判定が honden 生来の報告行にも当たり、`raw` を YAML 原文で
上書きしていた。`coverageOf` の `json_extract(r.raw, '$.status')` が

同じ型の見落としの 8 度目である。

`origin`（native / import）を持たせ、影は影の行だけを触る形にした。

### ② 行頭が `--` の削除行を、ファイル頭と取り違える

`parseUnified` が hunk の中身でも `--- ` / `+++ ` をファイル頭として解釈していた。
根本は `@@ -a,b +c,d @@` の **b と d を捨てていた**こと——hunk の終わりを
行数で判じられない。

SQL のコメント（`-- `）を消す行は差分上で `--- ` になる。それを頭と読むと
hunk が打ち切られ、残った切り株が locate に成功して、
**「当たった」と言いながら何も変えない。**

「全部当たるか何も書かぬか」という核心の約束を、silent no-op で破っていた。

行数を数える形にした。ただし**数は目安**にとどめる——手で書いた差分は数がずれる。
境目は形で見分ける（`@@` と `diff --git` は紛れようがない。`--- ` は次が `+++ ` なら頭）。

数が残っている間に印の無い行が来たら断る。黙って閉じると fail-open になり、
読めなかったものを「hunk が終わった」と取り違えて通す。

### ③ 同じファイルが差分に二度出ると、前の変更が黙って消える

agent 名を本番と被らせぬ（testkaro）ことで回避した。

### 四、旧 watcher は「送れなかった」と言いながら三回届けた（記録）

### 六、L2/L3 実弾と、reset 後の記憶喪失（2026-08-27 13:00〜13:06）

### 七、急報の二本立て — reset せずに作業中の者へ届ける（2026-08-27）

殿の求め: 「リセットはしたくないが、作業範囲の増減のような急報は速く
届けたい。claude は切りのいい所で見るが、cursor は完了まで見ない」。

CLI ごとに「作業中の入力」の扱いが違うことが実測で判っておる:

| CLI | 作業中に send-keys で届いた文 |
|---|---|
| claude | 切りのいい所（ツールの合間）で読む |
| codex | 完了まで読まぬが、確認キーで見られる（Tab 仮置き・実測校正待ち） |
| cursor | 完了まで読まぬ。確認キーも無い |

答えは push と pull の二本立てにした。

**push（nudge の添え押し）**: 急ぎ（URGENT_TYPES = clear_command / cmd_new /
cmd_update）の合図に限り、本文 + Enter の後に CLI 別の follow-up 確認キーを
添え押しする（FOLLOWUP_KEY・今は codex: Tab のみ）。急ぎでない合図には
押さぬ——UI の状態を無闇に触らぬ。

**pull（出力への横乗せ）**: cursor は作業中も**ツールとして honden は叩く**。
そこで全コマンドの出力の尻に、呼び出し主の急ぎ未読を一行だけ横乗せする
（urgentRideAlong / main.ts ridealong）。作業の真っ最中でも、次に honden を
叩いた瞬間に「⚠ 急ぎの未読（cmd_update=1）」が目に入る。除外は inbox 系
（見に行く行為そのもの）と nudge（末尾 JSON が芯への返事）。急ぎでなければ
載せぬ——毎回うるさくすると読み飛ばしが癖になり、いざの一行まで死ぬ。

実機の陽性対照: ashigaru2（cursor）に cmd_update を積み、ashigaru2 として
claim check を叩く → 出力の尻に ⚠ 行が載った。inbox unread には載らぬ。

これで梯子が揃う: 急報は横乗せ+添え押しで作業を壊さず届き、
それでも無反応なら段梯子（L1→L2→busy 延期つき L3）が控える。
reset は最後の砦であり、初手ではない。

**追補（殿裁定・同日）**: 横乗せは cursor 専用の裏路ではなく**全 CLI 共通の
第一経路**とする。send-keys の届き方は CLI ごとにまちまちだが、「作業中も
ツールとして honden を叩く」ことに CLI 差は無い。push（nudge・添え押し）は
補助へ回る。受け手の作法にも「作業の節目で honden を叩けば急報が載る」を
共通の前提として書く（指示書統一 cmd_712 で反映）。

### 十一、cursor hooks 調査と実測 — reset 後の再装填が公式機構で塞がる（2026-08-27 19:05）

殿の指示で agy（Antigravity/Gemini・pro）に deep research を委譲し、
公式 docs（https://cursor.com/docs/hooks）の直読と、試験環境 cursor での
最小実験で裏取りした。

**機構（docs 直読で確認）**: `<project>/.cursor/hooks.json`（または
`~/.cursor/hooks.json`）・version 1。フックは任意の shell を子プロセスで
実行し、stdio の JSON で双方向通信。イベントは sessionStart / sessionEnd /
preToolUse / postToolUse / postToolUseFailure / beforeSubmitPrompt /
beforeShellExecution / afterShellExecution / preCompact / stop(loop_limit) 等。
**sessionStart と postToolUse は `additional_context` で会話へ文脈を注入できる**。

**実測（cursor-agent v2026.08.25・試験環境）**:
1. sessionStart フックは **CLI で発火する**——ただし**プロセス起動時に一度**。
   走行中に hooks.json を置いても既存プロセスは拾わぬ（IDE の自動リロードと
   違う）。再起動で発火（ログで証明）
2. `additional_context` の注入は効く——合言葉「山吹」を仕込み、会話で
   訊いたら一語で返った
3. **`/new-chat`（= L3 reset）後の新会話にも注入が効き続ける**——バナー 2 つで
   新会話を確認した上で、合言葉が再び返った。再発火はせぬが文脈は残る

**含意——残る本丸「reset 後の再装填」の答え**:
cursor（T1）は project の `.cursor/hooks.json` sessionStart に受け手作法を
仕込めば、L3 reset 後も作法を失わぬ。九で見た「記憶喪失の大捜査」は
この機構で塞がる。claude は CLAUDE.md 自動読込、codex は AGENTS.md が
同じ役を担う——**三者三様の再装填経路が揃い、指示書統一（cmd_712）の
設計に「CLI 別の常設経路」として組み込める**。

agy の報せで未確認だった点の裏取り結果: 「事後フック出力が LLM に届かぬ
バグ」は未検証のまま（我々は sessionStart しか使わぬので急がぬ）。
「外部からの割り込み注入フックは無い」は docs のイベント表と整合——
nudge / 横乗せの続投が正しい。

実験に使った `.cursor/hooks.json` と `session-start.sh`（試験環境の受け手
作法+合言葉つき）はリポジトリに残す。合言葉は将来の再検証の陽性対照。

### 十二、禁じ手の門 — D 表を訓戒から鍵へ（2026-08-27）

殿の構想: 機械層で禁じ手を止め、正当な例外は将軍が裁定して OTP を発行し、
実行者がそれを打って一度だけ通す。「この環境なら将軍（Fable/Opus 級）が
コマンドを自律レビューできる。プロンプトインジェクションで反旗を翻された
時のため、コマンドを先に見てけしからん理由なら拒否する」。

**実装**: 判定器は `src/guard.ts` 一つ（D001-D010 の紋様・OTP の発行と検め）。
CLI ごとの皮は薄く——cursor は `beforeShellExecution`（failClosed）、
codex は `PreToolUse`。OAL と同じ流儀である。

三層の裁き: allow / deny+直訴可 / deny+**絶対域**。絶対域（D001 rm -rf /・
D007 mkfs/dd・D008 pipe-to-shell）は手形でも通さぬ——**将軍すら注入で誤る
日の保険**である。将軍自身が開けられぬ扉を一枚残す。

OTP の束縛: sha256(env 前置を剥いだ本体) + 宛先 agent + 期限（既定 10 分）
+ 一回性。平文の札は発行の瞬間にしか存在せず、正本にはハッシュのみ残る。
無害な件で札を取り危険な件へ流用する手は通らぬ。

**実弾で通した全ループ（cursor）**:
```
足軽 pkill → 門 deny + 直訴の作法を agent_message で返す
  → cursor が自走で honden guard appeal（教えておらぬ・作法の文だけが頼り）
  → 将軍の inbox へ urgent 到着 → 検分 → guard grant
  → inbox で札が届く → HONDEN_OTP=札 を頭に付けて再実行 → 一度だけ通る
  → 台帳に guard.pass（actor=ashigaru2・cmd_hash 一致）
```

**実弾が釣った穴 二つ**（いずれも修正・回帰試験つき）:
1. **env 前置で門が素通り**——`X=1 pkill …` は行頭アンカーを外す。
   判定も手形の束縛も `stripEnvPrefix` した本体に対して行うよう改めた。
2. **9p 番人が相対パスを素通し**——`$HOME/…`（非展開）が実際に
   `/mnt/c/…/honden/$HOME/` に正本を作った。`resolve()` してから検める。

**codex の門（殿の最大の懸念）**: `--dangerously-bypass-approvals-and-sandbox`
は承認もサンドボックスも消す。だが hooks は生きておった——実測:

```
permission_mode: "bypassPermissions"  ← YOLO そのもの
tool_input.command: "pkill -f zzz… && touch /tmp/zzz_blocked"
→ 門が deny を返し、codex 自身が「ガードによりコマンドは実行されませんでした」
→ 的（/tmp/zzz_blocked）は出来ておらぬ
```

**AppArmor を持ち出さずとも、YOLO codex に門が掛かる。**

ただし codex 特有の落とし穴が二つ:
- **未信頼のフックは黙って飛ばされる**。`codex exec`（非対話）には信頼を
  与える出口が無く、足跡ゼロで素通りする。門を配るには**各機で一度だけ
  対話起動し `/hooks` で信頼を与える**手順が要る。
  信頼は `~/.codex/config.toml` の `[hooks.state]"<path>:<event>:<i>:<j>"`
  に `trusted_hash` として刻まれる。
- **hooks.json を書き換えるとハッシュが変わり、再レビューまで門が飛ぶ**。
  これは fail-open である——[[新しい層は fail-open として生まれる]] の型。
  起動時に門が生きておるかを確かめる仕掛けを運用に組み込むこと。
- 出力の綴りにも罠がある: codex の PreToolUse は `systemMessage` しか受けず、
  `continue`/`stopReason` を返すと**フック失敗と見なされツールが続行される**。
  deny は `hookSpecificOutput` 一本で言う。

**限界**（誇張せぬために書く）: 紋様は明白な形しか止めぬ。D011（意図ベース・
分解・難読化）は捕まらぬし、参照した記事の実例でも「別の方法で回避されて
いる」。門は多層防御の一枚であり、訓戒（プロンプト層）と将軍レビューを
置き換えるものではない。**D 表の一部が鍵級へ昇格した**——それが今日の戦果である。

### 十三、将軍を縛る鍵は将軍の外へ（殿構想・**今は作らぬ**）

十二の門には穴が一つ残っておる。**将軍が検分役と鍵役を兼ねておる**ことだ。
将軍が注入で反旗を翻せば、直訴→裁定→手形の輪ごと落ちる。将軍が自分を
縛れぬのは、鍵が将軍の process の中にあるからである。

殿の答え: **Proton Pass 等が出す時間猶予つき OTP を使う**。鍵の種は殿の
端末にあり、将軍はコードを作れぬ。将軍にできるのは検分と進言までで、
実際に門を開けるのは殿の authenticator だけになる。

殿はこうも言われた——「時間猶予を持つ OTP は普通は脆弱性そのもの」。
その通りである。だがここでは**猶予の窓が features になる**: 窓が
再送の隙を作るのと引き換えに、鍵を将軍の外へ出せる。しかも十二の束縛
（cmd_hash + 宛先 + 一回性）が既に効いておるゆえ、窓の中で拾われた
コードも**別のコマンドには使えぬ**。汎用 TOTP の再送問題より遥かに狭い。

作る時が来たなら:
- 種は honden の正本に置かぬ（置けば将軍が読める＝意味が消える）
- 段は四つになる: allow / deny+将軍の手形 / deny+**殿の TOTP** / 絶対域
- 殿の TOTP を要する段は「将軍が正当と見立てたが、将軍を信じ切れぬ類」
  ——本番への push、秘密に触れる操作、他エージェントへの介入など

**今は作らぬ**（殿明言 2026-08-27）。門の第一形が実弾で通ったばかりで、
使い込んで穴を出すのが先である。ここに書いたのは、忘れぬためだけの覚書。

### 十四、直訴の検分を別の器で（殿構想・見立て）

殿の案: 直訴文を「context fork か何かした専用スキル」で見れば、注入の
危険を若干緩和できるのではないか。トークン代に見合うかは分からぬ、と。

**一点訂正**: fork は親の文脈を引き継ぐ。汚染を逃れる器に汚染ごと
持ち込んでは意味がない。要るのは **まっさらな subagent**（fork ではなく
新規）である。渡すのは正本から引いた事実だけ:

```
渡してよい: コマンド実体 / 直訴者 / その者の task と cmd の系譜 /
            取り置き（claims）/ 直近の報告 —— すべて DB から引いたもの
渡してはならぬ: 将軍の会話文脈、直訴者の弁明を「前提」として
```
弁明は渡してよいが **データとして** 渡す。「〜と申しております」の形にし、
検分者の指示として読ませぬ。返しは自由文でなく型を切る（verdict / rule /
reason）——**検分者の出力が将軍へ注入し返す経路も塞ぐ**ためである。

**何が緩和され、何が残るか（誇張せぬために分けて書く）**

| 穴 | 別器の検分 | 殿の TOTP（十三） |
|---|---|---|
| 将軍の**文脈が汚染**されておる | ○ 緩和する | × 効かぬ |
| 将軍**そのもの**が反旗を翻す | × 効かぬ（鍵は将軍が持つ） | ○ 塞ぐ |

二つは別の穴を塞ぐ。どちらかで足りる話ではない。

**代の見立て**: 検分は **直訴の時だけ** 走る。直訴は「機械層が止め、かつ
絶対域でない」時にしか起きぬ——force push・reset --hard・pkill の類で、
この布陣なら週に数回。一回あたり数万トークンなら、**常時走る横乗せや
nudge と違って代は無視できる**。見合わぬのは頻度が上がった時だが、
その時は掟の紋様が広すぎる（false-positive が多い）という別の報せである
——代が「門が邪魔者になっておらぬか」の計器になる。

**やらぬ理由が今のところ無い**が、門の第一形が出たばかりゆえ、
実際の直訴を数件見てから型を決めるのが順である（何を渡せば足りるかは、
実物を見ぬと決められぬ）。

### 十五、検分者の器 — plugin.json は要らぬ。要るのは道具の剥奪（2026-08-27）

十四の「別の器」を Claude Code でどう建てるか、公式仕様を当たった。

**plugin.json は要らぬ**。`~/.claude/agents/<name>.md` を置けば全ての作業場で
subagent として名乗れる（`.claude/agents/` は作業場限定で、そちらが優先）。
`.claude-plugin/plugin.json` が要るのは **束ねて配る時**——複数の skill や
agent や hook を一つの plugin として渡す、marketplace に出す、版を切る、
といった場合だけである。将軍が自分の machine で使う分には不要。
（配置の罠: plugin 化する時 `agents/` と `skills/` は plugin **root** に置く。
`.claude-plugin/` の中ではない。）

**skill は別文脈を作らぬ**——十四で警戒した落とし穴は公式仕様として裏が
取れた。skill の中身は**親のセッションへ読み込まれる**。図にあった
`skills/*/agents/*.md` は、その skill を plugin 化して初めて subagent として
起きる。置いただけでは隔離にならぬ。
`/subtask` は**親の会話履歴を引き継ぐ** fork ゆえ、我らの用には使えぬ。

**道具の剥奪は仕掛けで効く**（十四の要点の裏取り）。frontmatter で
`tools:`（allowlist）・`disallowedTools:`（denylist）・`permissionMode: plan`
（読むだけ）が指定できる。

**そして、ここで一つ気づいた穴がある。**

`honden guard grant` は「将軍のみ」を **pane の @agent_id** で見ておる。
subagent は将軍と同じ pane に居るゆえ、**Bash さえ持たせれば検分者も
「将軍」として手形を切れてしまう**。名乗りでは守れぬ。

ゆえに検分者に **Bash を持たせてはならぬ**:

```yaml
tools: Read          # これだけ。Bash なし＝手形を切れぬ
permissionMode: plan
```

事実の束は**親（将軍）が先に作って置く**:
```
将軍:   honden guard appeal show <id> --facts > <束>
検分者: その束を Read するだけ
```
これは十四で書いた「事実集めを検分者の裁量にしてはならぬ」と同じ形に
自然に落ちる——検分者は自分で調べられぬゆえ、都合の悪い証拠を避けることも、
手形を切ることもできぬ。**道具の不在が、そのまま権限の境界になる。**

### 十七、検分者の試運転 — 二つとも DENY、うち一つは将軍より正しかった（2026-08-27）

> 一言も述べておらぬ。**門を開けずとも任は果たせる。**

### 十八、構文解析の門（Rust）— 建てる合図を先に決めておく

殿の見立て: 紋様のままでは対症療法が続く。Rust で AST らしく処理せねば
ならぬのではないか。ただし主要な形はある程度で落ち着きそうでもある。

**AST の一番の値打ちは、紋様の精度ではない。**
いまの門は**知らぬ形に出会うと通す**（fail-open）。`X=1 pkill …` の素通りが
それで、手で一枚継ぎを当てた。構文を解けるなら逆の構えが取れる:

```
解けた命 → 掟に照らす
解けぬ命 → 止める（直訴可）  eval / $(…) / `…` / bash -c "$VAR" / base64 等
```

**知らぬものを通す門から、知らぬものを止める門へ。** 理解できる形を宣言し、
残りを拒む。継ぎを一枚ずつ増やす道から降りられる。紋様の精度向上は副産物。

**買えぬもの**: 構文が解けても意図は読めぬ。`rm -rf $DIR` の中身は走らせる
まで判らず、スクリプトに書いて呼べば見えず、`find -exec` も同じ。
D011 は AST の外に残る。層はこうなる:

| 層 | 受け持ち | 対症療法が終わるか |
|---|---|---|
| 構文（AST） | 解ける形を裁き、解けぬ形を止める | **終わる** |
| 意図（訓戒・検分者） | 分解・難読化・なぜそれをするのか | 終わらぬ |
| OS（AppArmor 等） | そもそも触れなくする | 別の話 |

**置き場所**: `core/watch` は依存ゼロで作ってある（常駐・低メモリの要件）。
解析器は**別 crate**（`core/guard` 等）に置き、芯に混ぜぬこと。既存の POSIX
shell parser を借りる（自作は引用・here-doc・展開順の罠が深い）。候補の版と
保守状況は建てる時に要確認。

**建てる合図**: 落ち着くのは**掟の側**であって、継ぎが増えるのは**解析の側**
である。今日すでに一枚当てた（env 前置）。ゆえに——

> **解析の形の穴を三枚目に継いだら、その時が建て時。**

一枚目は済み。二枚目で「型が見えた」、三枚目で「継ぎ当てでは終わらぬ」の証。
数えるだけなら代はかからぬ。継いだ時はここに一行足すこと。

継ぎの数え（**ここが正。継いだらここに足す**）:

1. 2026-08-27 env 前置（`X=1 pkill …` で行頭錨が外れた）→ `stripEnvPrefix`
2. 2026-08-28 経路の概念が型に無い（`Edit`/`Write` 経由の書き込みが門の外・
   ファイル宛先を掟に書けぬ）→ 当座は CLI 側 deny と D012/D013 で凌ぐ
3. 2026-08-29 旗と値の対（`tmux -L sock send-keys …` で副命令を見失う）
   → 旗と値を読み飛ばす細工。**argv の配列が手に入るなら要らぬ継ぎ**
4. 2026-08-29 **引用の中の字面が、命と区別できぬ**。deny の一覧を編む python の
   heredoc に、その一覧そのものが現れて己の門に弾かれた（将軍が二度踏んだ）

**三枚を越えた。合図は鳴っておる（2026-08-29）。**

四枚目が最も雄弁である。`python3 <<'EOF' … 危うい字面 … EOF` は
**heredoc の中身**であって命ではない。構文を解けば一目で分かり、紋様には
永遠に分からぬ。しかも**誤検知の側から**同じ結論が出た——知らぬ形を通す門は、
知らぬ形を止めもする。精度の話ではなく、構造の話である。

三枚目も同じ性質。副命令を見つけるのに旗と値を読み飛ばす細工が要ったが、
argv の配列が手に入るなら `argv[1]` を見るだけで済む。

一方、**AST でも買えぬもの**も今日はっきりした。`cd dir && cat 秘密` のような
**場所と名の分割**は、構文を解いても cwd を追わねば分からぬ。tmux の前方一致
（`send` = `send-keys`）は shell でなく tmux の文法ゆえ外に残る。
三層の表（構文／意図／OS）はそのまま生きておる。

### 十九、旧環境の権限設定を継承した（2026-08-28）

殿の下知で二つを honden へ移した。

**`.claude/settings.json`** — `permissions`（allow 7・deny 20）・`attribution`・
`spinnerVerbs`。hooks は除いた（shogun repo のスクリプトを指しており、

deny 一覧は D 表そのものである。**禁じ手の門（十二）と重複しておるが、
重複ではない**——層が違う。honden guard は hooks 経由で全 CLI に効き、

**`config/opencode-permissions.yaml`** — 役×ファイル境界の権限表。そのまま写した。

**写して初めて見えたこと: 構造の変更が、静かに縛りを解いていた。**

台帳へ刻むようにした。

陽性対照で一つ釣れた: 最初の実装は早期 return より後ろに刻んでおり、
**空の inbox を覗いた時だけ跡が消えた**。「覗いたが空だった」も覗きである。
list の直後へ移し、空でも残る・自分のを読んだ時は残らぬことを両対照で確かめた。

**残る宿題**: この表の他の縛りも同じ検めが要る。tasks / reports / dashboard /
saytask の役分けが、DB へ寄せた後どこまで生きておるか。今日見たのは inbox
一つだけである。切り替え前に一枚の表にして突き合わせること。

### 二十、権限表の突き合わせ（五十体の検分）と、門の自衛（2026-08-28）

十九の宿題を果たした。五方面（task / report / dashboard・saytask /
cmd-queue / common.edit_deny）へ検分役を放ち、抜けの申し立てには**反証役**を

**最も重い二筋を先に塞いだ。**

**一、布陣の外から役職を名乗って権を振るえた**（`bc55e75`）。
inbox write は最初からこれを塞いでいたのに、**同じ防御が task assign /
cmd new / report qc / decide / guard grant へ配線されておらぬ**。外から
`HONDEN_AGENT_ID=karo` で足軽へ振れ、しかも振られた報せの差出人は

`(?![\w.])` で締めた。**門を広げるたびに、門が邪魔者になる道も広がる。**

**残る穴（塞いでおらぬ・優先順）**

| 筋 | 中身 | 見立て |
|---|---|---|
| 読みの漏れ | `lease` / `claim` / `cmd show` / `guard facts` が名乗りを取らず、他人の任・報告・司令を跡も残さず晒す | inbox と同じ「禁じぬが跡を残す」型で揃えるのが筋 |

| patch の無門 | `honden patch` が名乗りを取らず `--root` も呼び手任せ | honden 自身が任意書き込みの道具を提供しておる |
| pane 名乗りの書換 | `@agent_id` は pane の属性ゆえ、当のエージェントが `tmux set-option` で書き換えうる | 名乗りの根が揺らぐ。要検討 |
| 門の追跡外 | hook 設定・スクリプト・binary が `.gitignore` の全除外に落ちており、細工しても `git diff` に出ぬ | 見張りの目が届かぬ |

`dashboard` / `saytask` / `ntfy_inbox` は honden に機構自体が無く、
「移していない」だけである（穴というより未着手）。


### 二十一、残り六筋を塞いだ（2026-08-28）

二十で挙げた残りに取り掛かった。**五筋を塞ぎ、一筋は帯が違うため送った。**

**読みの漏れ**——inbox.peek と同じ「禁じぬが跡を残す」型で揃えた。
`lease` / `claim` は働く者が皆の分を見た時だけ刻む（差配役が全体を見るのは
職分ゆえ刻まぬ——線の意味はそこに残す）。`guard facts` は他人の束を引いた
時に刻む。実弾で六対の陰陽を確かめた: 陽性（足軽の lease/claim/他人の束/
patch/import）はすべて刻まれ、陰性（家老の lease・自分の束）は刻まれぬ。

**import の無門**——台帳の actor が `'import'` 固定で、誰が影を差し込んだか
辿れなかった。`by` を通し、実行者の名乗りを刻むようにした
（実測: `gunshi → source.add`）。

**patch の無門**——honden 自身が提供する任意書き込みの道具でありながら、
誰がどこへ当てたか残らなかった。`patch.apply` を刻む

**門の追跡外**——`.gitignore` が全除外のホワイトリスト方式で、hook 設定も
hook スクリプトも追跡外に落ちていた。**門を外す細工をしても git diff に
何も出ぬ。** 門は、外された時に気づけて初めて門である。追跡下へ入れた。

**名乗りの根**（D013）——honden は布陣内の名乗りを pane 属性 `@agent_id`
から引くが、それは**その pane に座る当人が書き換えうる**。書き換えられれば
以後の名乗りはすべて偽となり、台帳の actor まで偽になる——**跡が嘘をつく方が、
跡が無いより悪い。** `tmux set-option … @agent_id` の形を止めた（直訴可・
布陣を組み直すのは正当な仕事ゆえ）。読む形（display-message / list-panes）は通す。

**送った一筋**: 経路型の掟（honden guard はコマンド文字列のみを見て、
ファイルの宛先という概念が型に無い）。これは十八の構文解析と同じ帯の話で、
紋様を継ぎ足す道では終わらぬ。**継ぎの数え**に二枚目として記す。

継ぎの数えは**十八に一本化した**（2026-08-29）。ここに写しを置いておったが、
合図を宣言した所と継いだ所に数えが分かれ、どちらも権威にならず続かなくなった。
**二箇所にある数えは、どちらでも維持されぬ。**


### 二十二、claude の門と、門の生存確認（2026-08-28）

**claude の門**（T1 最後の一枠）。`.claude/hooks/guard.sh` → `honden guard hook
claude`。受け答えの形は codex と同じゆえ（codex が claude の形を写した）、
実装は一つで足りる——皮を分けるのは呼ばれ方の違いだけで、判定器も応答も共有する。
これで T1 三種すべてに門が掛かった。

なお `.claude/settings.json` の `permissions.deny` とは層が違う。あちらは
Claude Code 内蔵の紋様照合で、こちらは honden の判定器を通す——同じ掟を
一箇所で持つための道である（deny 側は honden を通さぬ道の保険として残す）。

**`honden guard selftest`** —— 本日繰り返し出た「据えただけでは効かぬ」への答え。

静かに門が消える形を、一日で三度見た:
- codex は**未信頼の hook を黙って飛ばす**（`codex exec` に信頼の出口が無い）

いずれも静かである。静かに消えるものは、定期的に叩いて確かめるほかない。
設定を読んで「据わっておる」と判ずるだけでは足りぬ——**皮を実際に走らせ、

codex については信頼の記録（`~/.codex/config.toml` の `[hooks.state]`）が

**計器そのものを検めた**（陰性結果を陽性対照なしに信じぬため）:
claude の皮を空にすると `**効いておらぬ**` と赤が出て終了コードが 2 になり、
戻すと緑で 0 に戻った。**門を外して赤を見た**——この計器は検知できる。

据わっておらぬのは見れば分かる。危ういのは「据えたつもりで効いておらぬ」で、
selftest はそこを名指しする作りにした（`configured && !denies` を別扱い）。

### 二十四、旧環境の二つの hook を移した（2026-08-28）

殿の問いで気づいた——十九で `.claude/settings.json` を継承した際、
**hooks 節を「shogun repo のスクリプトを指すゆえ」と除いていた**。
だがその二つは、honden の急所にそのまま刺さる代物だった。

**`session_start_hook.sh` → `.claude/hooks/session-start.sh`**

起動・resume・`/clear`・compaction のいずれでも「そなたは誰で、まず何をするか」
を確定的に注入する。生まれた訳は persona 崩壊事故（家老が「我は将軍」と
名乗った・2026-04-19）で、**推測させぬのが要**——名乗りを pane から
確定的に読み出し、その名で語りかける。

これで **T1 三種すべてに再装填の経路が揃った**:

| CLI | 経路 |
|---|---|
| claude | この hook（+ CLAUDE.md 自動読込） |
| cursor | `.cursor/hooks.json` の `sessionStart`（`additional_context`） |
| codex | AGENTS.md 自動読込 |

九で「reset 後の記憶喪失に道標が無い」を最重要の欠けとして挙げたが、
**塞がった**。honden 版では受け手の作法（read → ack）と**急報の横乗せ**
（作業の節目で honden を叩けば ⚠ が載る）を必ず含めるようにした。

**`stop_hook_inbox.sh` → `.claude/hooks/stop-inbox.sh`**

手を止める前に未読を検め、残っておれば止めるのを断る。
**現行 CLAUDE.md の「MANDATORY Post-Task Inbox Check」を機械にしたもの**である
——「これは任意ではない」と書いても守られぬ日が来る。ここで機械が止める。

効き目は作法の徹底だけではない。**合図に頼る度合いが下がる**——手を止め
ようとした時に自分で未読を拾うなら、外から起こす要が減る。現行 CLAUDE.md が
「優先度1: agent self-watch」と呼ぶものの実体である。

**旧版から削ったもの**（移さぬ判断も記す）:
- idle フラグの世話——honden の合図は pane を写して busy を見るゆえ要らぬ
- `inotifywait` での待ち伏せ——芯が配る。ここで待つと二重になる
- **最後の一言を読んで家老へ自動で報せる件**——文面の紋様で「完了」を
  判ずるのは危うい。報告は agent が `honden report submit` で出すのが筋で、
  hook が代わりに騙るべきではない

**輪を断つ手当ては移した**: 一度止めた後（`stop_hook_active`）は通す。
無ければ block → Stop → block と回り続け、agent が永久に手を止められなくなる。
二度目で通し、それでも残るなら段梯子（L1/L2/L3）が拾う——層の分担である。

陰陽の対で実測: 名乗り無しは黙る／差配役には重い手順／未読ゼロは通す／
未読ありは block／将軍の pane は止めぬ／二度目は通す。**六対すべて意図どおり。**


### 二十五、圧縮の後にも仕込む（殿の問い 2026-08-28）

「コンパクション完了後にも仕込む？」——検めたところ、**三者で事情が全く違った。**

**codex は据わっておらなんだ。** `.codex/hooks.json` には門（PreToolUse）しか無く、
**SessionStart すら無かった**。codex の足軽は起動時も圧縮後も、名乗りも作法も
受け取っておらぬ。二十四で claude 側だけを見て済ませた見落としである。
据えた上で、codex が持つ **`PostCompact`** からも同じ皮を呼ぶようにした
——圧縮で文脈が薄れた後こそ名乗りを言い直す要がある、という殿の見立てのとおり。
陽性対照で `additionalContext` が返ることを確認。

**cursor は hook では塞げぬ。** `preCompact` は**観測専用**である
（docs 明記: 「圧縮を止めることも変えることもできぬ」。返せるのは
`user_message` = 人に見せる文のみ）。そして **`postCompact` に相当するものが無い**。
ゆえに cursor は「`sessionStart` の `additional_context` が圧縮を生き延びるか」に
懸かっており、そこは**未検証**である。生き延びぬなら、急報の横乗せ
（どの副命令の出力にも ⚠ が載る）が最後の頼みとなる。

**claude は覆っておるはずだったが、推測に懸かっていた。**
公式仕様を当たって二つ判った:

1. **公式は `compact` matcher での再注入を明記して勧めておる**——
   「圧縮は大事な細部を失わせる。SessionStart hook に compact matcher を付けて
   圧縮のたびに重要な文脈を注ぎ直せ」。殿の問いは docs の推奨そのものであった。
2. **matcher を省いた時の挙動は docs に書かれておらぬ。** 実装からの推測でしか
   「全部で発火する」と言えぬ。旧環境の CLAUDE.md が `matcher=clear/compact` と
   書きながら実際の settings.json には matcher が無い、という食い違いも
   ここから来ておる。

**門の生死が推測に懸かる形は避ける。** matcher を
`startup` / `resume` / `clear` / `compact` / `fork` の**五つに開いて明示**した
（束ねる書き方 `"a|b"` も SessionStart で効く確証が無いゆえ使わぬ）。
`fork`（worktree の分岐）は今日初めて知った値である——分岐した先でも
名乗りは言い直すべきゆえ入れた。

なお claude にも `PostCompact` はあるが（matcher: manual / auto）、
**注入の可否と順序が docs で確かめられぬ**ゆえ使わぬ。
公式が明記しておる `SessionStart(compact)` 一本で足りる。

**Stop hook の作り**も裏が取れた: top-level `decision: "block"` は現行仕様であり、
`stop_hook_active` も入力に含まれる。加えて**八度続けて止めると Claude Code 側が
押し切る**とのこと——我らは一度で通す作りゆえ、そこまで至らぬ。

### 二十八、布陣の様子を一枚に（2026-08-28）

旧 `scripts/agent_status.sh`（258 行・bash + python + yaml）の移植。
だが honden では**書き直すほどのものが無かった**——並べる値はすべて
正本と busy の見立てに既に在る。

| 並べるもの | 出所 |
|---|---|
| 顔ぶれ・CLI・模型 | roster 表 |
| pane の在り処 | tmux（src/pane.ts） |
| 手が塞がっておるか | pane を写して見立てる（src/busy.ts・門と同じ紋様） |
| 任と其の様 | task 表 |
| 持ち場の貸与 | lease（期限切れの印つき） |

旧は task YAML と inbox YAML を python で開いていた。正本を一つに寄せた今、
開く先も一つである。ゆえに bash ではなく `honden status` として建てた
（`--json` で機械にも渡せる）。`shutsujin.sh status` からも呼ぶ。

**試験で守った二つ**

一、**「居らぬ」と「手すき」を混ぜぬ。** pane が無い者の busy は
`null` であって `false` ではない。false と書けば「不在」が「待機」と出て、

### 三十一、陣の bash に履歴を残させぬ（殿の申し出 2026-08-28）

### 三十三、hook の信頼は「立て直すたび」ではない — 将軍の見立てを殿が正された（2026-08-28）

→ **問われなんだ**。本番の陣で毎回問われぬのも同じ理である。

**真因**: 直前の立て直しの折、`.codex/hooks/session-start.sh` の**註を書き換えて**
いた（「実機で決着した」の一文を足した）。すなわち切れる条件は
「pane を立て直した」ではなく「**hook の中身が変わった**」である。
しかも `hooks.json` だけでなく**呼ばれるスクリプトの中身**まで見ておる
（`trusted_hash` が命令の文字列だけでは合わなんだのも、これで説明が付く）。

**正しい形**:

| することは | 信頼は |
|---|---|
| pane を立て直す・CLI を替える | 切れぬ |
| `hooks.json` を書き換える | 切れる |
| **hook のスクリプトの中身を直す（註だけでも）** | **切れる** |

**書きぶりの誤りも一つ正す。** 二十で「静かに門が消える形」を三つ挙げたが、
そのうち「hooks.json を書き換えると再飛び」は**中身の変更全般**へ広げるのが正しい。
註を一行足しただけで門が飛ぶ——これは配布の時により厄介である。
`honden guard selftest` が要るのは、まさにこの静けさゆえ。

**将軍の見立てを、実測より先に書いてはならぬ。** 三度問われた事実は正しいが、
「毎度出る」は測っておらぬ推測であった。殿が使うておられる本番の陣という

### 三十六、段梯子に終わりが無かった（2026-08-28・一巡試験の最大の収穫）

### 三十九、素直に読めば本文を壊す — 殿の指摘（2026-08-28）

### 四十四、切り戻しの綱 — `honden export`（殿の下知 2026-08-29）

「yaml 書き出し一応作っておいて。やりたくはないが、切り戻し時に有用」。

**常時の書き戻し（併走）は作らなんだ。** 書き手が二人になれば、どちらが正か
分からなくなる。作ったのは**切り戻す瞬間に一度だけ吐く**一方向の写しである:

```
honden export --out <新しい場所>
  queue/shogun_to_karo.yaml           司令＋受け入れ条件
  queue/inbox/{agent}.yaml            報せ（未読・既読を忠実に）
  queue/tasks/{agent}.yaml            任（workdir・branch は raw から復元）
  queue/reports/{agent}_report.yaml   最新の報告
```

**生きた queue/ へ直接は書かぬ。** `--out` 必須で新しい場所へ吐き、
配置は人の手——旧環境の queue/ を先に退避してから写す。吐いた跡は台帳に残る。

**検めは二枚の読み手で行った:**
- **round-trip**: 吐いた YAML を honden 自身の `import` が難なく取り込む
  （難ありゼロ・全枚）——形の正しさの機械証明
- **旧の読み手**: 切り戻し先で実際に読むのは python の yaml である。
  一巡試験の実データ 10 枚すべてが `yaml.safe_load` で読めた

厄介な字（Windows パス・三連引用・`$HOME`）の往復も試験で縛った——
旧 `inbox_write.sh` はこの手の字で壊れた。**綱が同じ轍を踏んでは意味が無い。**

なお、この試験を書く時に将軍自身がまた三連引用と heredoc の轍を踏んだ
（python heredoc に `'''` を埋めて SyntaxError）。**厄介な字は道具も選ぶ**。

### 百二十七、dashboard-viewer.py は ts 層で継いだ（2026-08-29）

旧 viewer は python 323 行の HTTP サーバで、**dashboard.md を読んで**配り、
**mtime** で更新を検知していた。honden には dashboard.md が無い（読む時に組む）
ゆえ、そのままの移植は成らぬ。二箇所を置き換えた:

- ファイル → `composeDashboard()`（CLI の `honden dashboard` と同じ関数）。
  端末で見るものと画面で見るものが寸分違わぬ——正本一つ・組み一つ。
- mtime → **台帳の末尾**（`MAX(id) FROM ledger`）。正本が動けば台帳が伸びる。
  ブラウザは 1.5 秒毎に `/api/version` を見回り、伸びた時だけ md を取り直す。

層の選定は ts。rs 核は「見張る・起こす」だけの最小者に保つ決め（核が肥えれば
常駐者の検分が難しくなる）ゆえ、HTTP で配る類の便利は全て ts 側へ寄せる。
`bun run build` の単体 binary に載るゆえ、python も pip も要らぬ——旧 viewer の
stdlib-only という美点は形を変えて残る。見た目（暗色・字組み・marked）は旧を
踏襲した。殿の目が慣れた画面を変えぬ。

しくじりも一つ: main の出口が `process.exit(await main(...))` ゆえ、serve を
張った直後に **返すと配りながら即死**する。口上だけ出て curl が繋がらぬ実測で
発覚。`serveDashboard` は SIGINT/SIGTERM まで resolve せぬ Promise を返す形に
改めた。「返り値が出口に直結する main では、居座る副命令は返ってはならぬ」。

### 百二十八、bot cli を半統合した——別 binary・同 repo（2026-08-29）

旧 scripts/github_issue_create.sh（bash 391 行・.tmp に置き去りで git 履歴からも
消えていた）を honden へ継いだ。`src/bot.ts`（純関数の芯）+ `src/botmain.ts`
（皮）→ `bin/honden-bot`。**半統合**の意は: repo と build は honden に同居させ、
binary は分ける——honden 本体（正本の書き口）と bot（外向き GitHub 書き込み）は
権限の性質が違う。混ぜれば「honden を持つ者は GitHub へ書ける」になってしまう。

道は三本になった。個人 token 三層と App の別を混同せぬこと:
- WSL の gh = RO。読み専用。誰でも可。
- gh.exe = 殿の個人 token（repo 全権）。**将軍のみ・配下禁止**（殿命）。
- honden-bot = App 名義（shogun-bot・Issues:write のみ）。**司令層のみ**。

旧版からの主な改め:
- 道具の依存が消えた: openssl + python3 + gh → Bun の crypto + fetch。
  JWT の署名は鍵ペアを作って verify で検める試験にした（「形が JWT らしい」
  だけの試験は署名の壊れを見逃す）。
- guard が本物になった: 旧は SHOGUN_AGENT_ID（env・自己申告）。今は pane の
  @agent_id（identity.ts・騙り不可）。本番の足軽 pane を借りた陰性対照で
  「ashigaru1 は落ちる」を実測済み。布陣外は殿の手と見なして通す——秘密は
  殿の家（~/.shogun）にあり、そこへ座れる者は元より全てを読めるゆえ。
- token cache を足した: installation token は 1 時間有効。600 で写し、
  期限 5 分手前で捨てる。鋳造の往復が毎回消える。
- ラベルは既存のみを機械で強制（殿命 2026-07-15 を訓戒から機械へ）:
  repo のラベル一覧と突き合わせ、無い名は付けずに報せる。
- 旧の既定ラベル shogun-bot,automated は廃した。無い repo で毎回警告になる
  だけの既定は既定でない。

### 百二十九、許状——cmd に縛られた多回券（2026-08-29）

殿の問い「同 cmd 内で使える reusable OTP とするか」への答えは**否**。手形
（guard_otp）はコマンド文字列の hash に縛られる作りで、起票は一件ごとに題が
変わる——「同じコマンドの再利用」では成り立たぬ。別の券として鋳た。

縛りは五重。**訓戒でなく正本の状態で効く**:

| 縛り | 効き方 |
|---|---|
| 者 | 渡した agent のみ（名乗りは系譜で錨・後述） |
| 陣 | **cmd が閉じれば刻中・回数残でも即失効**。`[cmd閉]` と見える |
| 的 | repo と verb（create/comment）を名指し |
| 数 | `--uses N`（既定 10・上限 200）。**撃つ前に引く** |
| 刻 | `--ttl-min`（既定 60・上限 480） |

回数を撃つ前に引くのは、失敗した弾を無料にすると**失敗し続ける限り無限に
撃てる**ゆえ。減った旨は必ず口に出す（黙って減らすと「なぜ尽きた」が辿れぬ）。

殿の挙げた発行の目安——個数が多い・能力十分・明示の指示——は**訓戒として
brief 側**に置き、機構には縛りと監査だけを持たせた。機構が「能力十分か」を
判ずることはできぬ。

### 百三十、名乗りの根を env から系譜へ移した（2026-08-29）

敵対レビュー（三つの目・13 agent）が critical を一件立てた。**我が設計の
誤り**である: honden 本体は「布陣外では権を振るえぬ」で fail-closed
（identity.ts の mayActAs）なのに、bot だけ「布陣外は殿の手」で fail-open に
した。`TMUX_PANE=` と空にするだけで足軽が布陣外を騙れた。

根が env にある限りこの種は尽きぬ。**系譜（親子）へ移した**（src/anchor.ts）:
tmux は各 pane の初発プロセス（pane_pid）を知る。我が身から親を辿り、いずれかが
pane_pid に当たれば、その pane が我が家。**系譜は kernel の持ち物で、
環境変数では書き換えられぬ。**

本物の足軽 pane（histjin %51）から実測:

| 騙り | 結果 |
|---|---|
| 素で whoami | ashigaru1 と判ぜられ退けられる |
| `TMUX_PANE=` で布陣外を騙る | **系譜が勝ち ashigaru1**。退けられる |
| `TMUX_PANE=%0` で将軍を騙る | **系譜が勝ち ashigaru1**＋騙りの跡として断り |

制御端末（tty）は使えなんだ——CLI の Bash 道具は端末を持たぬ子を産む
（我自身が tty_nr=0）。**見立てを書く前に測ったゆえ、無駄な実装をせずに済んだ。**

限界は正直に書く。全エージェントが同じ OS ユーザで走る限り、これは**堀で
あって城壁ではない**。app.pem は同じユーザが読めるゆえ、その気になれば錠前
ごと迂回して自ら JWT を鋳られる。真の境は uid 分離か仲介デーモンを要する。
ここが止めるのは「注入された足軽が honden-bot を呼ぶ」筋である。

**honden 本体にはまだ配線しておらぬ**（`HONDEN_AGENT_ID=karo honden cmd done`
が通るのを検分中に実見した）。核の watcher が起動した pane の名乗りを継いで
しまう懸念があり、そこは別途測ってから。Issue 化する。

### 百三十一、実弾で出た二つ（2026-08-29）

### 百三十二、足軽が自らに許状を切れた——入口の検めは漏れる（2026-08-29）

自律の見回りで、**己が作ったばかりの門を叩いて**発覚。本物の足軽 pane から
`honden guard charter --agent ashigaru1 …` を叩いたら **`EXIT=0` で通った**。

因は `mayActAs` の名にある。「may act as」ゆえ役職の検めに見えるが、実体は
**布陣外からの騙りだけを止める**もので、布陣の中は無条件で通す。ゆえに
入口の `actingAs('shogun')` は、布陣内の足軽に対して**何もしておらぬ**。

他の口は全て芯の側でも検めておった（createCmd の CMD_AUTHOR、guard.issue の
OTP_ISSUERS、raise の CAN_RAISE、decide の DECIDER、qc の QC_AUTHOR、
assignTask の ASSIGNER）。**我が許状だけが入口に頼っておった。**

塞ぎは `CHARTER_ISSUERS` を芯へ置くこと。併せて `mayActAs` の doc へ
「これは役職の検めではない」と大書した——名に騙される者は我だけではあるまい。

**戒め: 権の検めを入口だけに置くな。入口は増えるたびに漏れる。**

そしてもう一つ。**作ったばかりの門は、自分で叩け。** 単体試験は純関数を
九通り検めており全て緑であった。だが試験は `issueCharter` を直に呼ぶゆえ、
**CLI の門を通らぬ**。門を検めるには門を叩くしかない。

### 百三十三、移植で露出を広げておった——配信が全ての口に開いていた（2026-08-29）

前項の戒め「作ったばかりの門は自分で叩け」を他の新参にも当てたところ、
`dashboard --serve` で見つかった。旧 `dashboard-viewer.py` は
`HTTPServer(("127.0.0.1", PORT))` と**己の内に限って**おったが、`Bun.serve` は
hostname を渡さねば `0.0.0.0`——実測すると `*:8901` で開き、WSL の外向き
address（172.21.x.x）から **200 が返っておった**。

戦況には司令・裁可・陣容が載る。既定で外へ出してよいものではない。
WSL2 の mirrored networking では LAN にも出うる。

塞ぎ: 既定を `127.0.0.1` に。広げたい時だけ `--host` で明示し、その時は
断りを出す。陰性（外から 000）と陽性（`--host 0.0.0.0` で 200）の両方を実測。

**移植の折は「元が何を締めておったか」を見よ。** 機能は写したが締めを写さぬ
——これは新規実装より見つけにくい。元の一行（`"127.0.0.1"`）が、写した先では
**書かなかったこと**として消えるゆえ、差分にも現れぬ。

併せて `honden-bot repos` の門も足軽から叩いて確かめた（司令層のみ・EXIT=2）。

### 百三十四、落とした締めをもう一つ拾う——鍵の錠の検め（2026-08-29）

前項の型（移植で締めを写さぬ）を**両方の移植元へ当て直した**。

旧 `github_issue_create.sh` は `stat -c %a` で PEM の錠を検め、600 でなければ
警めておった。**我は写しておらなんだ。** 拾って `pemPermWarning` として据える。

写しを作る側（token.cache.json）は錠が効かねば書かぬと決めたが、鍵は**読む側**
ゆえ拒めば道具ごと死ぬ。旧に倣って声を上げるに留める。ただし 777 は DrvFs の
常であり、そこに鍵を置くこと自体が誤りゆえ「WSL ネイティブへ移せ」まで言う。

旧 python viewer の側も見直したが、道の検めは我と同じ**厳密な三つの当て**
（`/`・`/api/…`・他は 404）で、落としは bind 一つだけであった。

**しくじり一つ。** 陽性対照を取るのに**実物の鍵を /tmp へ写した**。後始末は
したが（消えたことを確認済み）、贋の鍵を作れば済む話であった。
`pemPermWarning` は純関数ゆえ試験に鍵は要らぬ——**実物を持ち出す前に、
持ち出さずに済む道を探せ。**

### 百三十五、戦況の窓を出陣に組み込んだ（2026-08-29）

殿の下知——`honden dashboard --serve` を出陣時に走らせよ、入口は
`pj_root/shutsujin_departure.sh` の名と場所で。旧環境の手が覚えておる形である。

**入口は根に、中身は scripts/ に。** 根の `shutsujin_departure.sh` は

出陣の書だけを根へ移すと他の script との並びが崩れるゆえ。

口の名・確かめ方・逃げ道（`--port`）まで言う物言いに直した。

### 百三十六、貝に試験を入れた——kagemusha が既に submodule であった（2026-08-29）

殿の問い「旧の置き方（bats + submodule 二本）を継いでテストを書くか」に対し、
将軍は「submodule は clone の摩擦を招くゆえ継がぬ」と答えた。**これは誤り。**
殿の一言で崩れた——**honden には既に kagemusha が submodule として入っており**、
`git submodule update --init` は元より要る。摩擦の話は成り立たなんだ。

**確かめずに論を立てた。** `.gitmodules` を見れば三秒で分かることを、見ずに
書いた。旧環境の 58 の bats のうち helper を使うは 16 と数えておきながら、
自分の repo の submodule は数えなんだ。

継いだ形: `tests/test_helper/bats-{support,assert}` を旧環境と**同じ commit**で
繋ぐ（v0.3.0-37-g0954abb / v2.2.4-2-g697471b）。新しい版を拾わぬのは、
旧環境で既に使われておる版をそのまま引くのが最も検めが済んでおるゆえ。

`tests/` は白名簿から漏れておった。**`git add -f` は使わぬ**（D009-AT 絶対禁）
——白名簿に一行加えるのが筋である。

**門は一つに。** `bun test` から bats を叩く橋を架けた（`test/shell.test.ts`）。
門を二つにすると片方が忘れられる。bats が無い時は**飛ばさず落ちる**——
道具が無いから飛ばすのは「新しい層は fail-open として生まれる」の型そのもので、
見張りが黙って消える。

速さも測った。素で 12 秒・四本並べて 2 秒。遅さの正体は計算ではなく
`sleep 2` 四回であったゆえ、落ち着きの間を `HONDEN_VIEWER_SETTLE` で
変えられるようにした（試験は 0）。全体で 3.5 秒に収まる。

### 百三十七、敵対レビューが 28 件・critical 三つ（2026-08-29）

戦況の窓を組んだ直後に三つの目で検めさせた。critical 三つはいずれも実物で

**二、DNS rebinding。** 錠も名乗りも無い口ゆえ、よその頁が己の domain を

**三、出陣を二度打つと、働いておる者の pane へ CLI の起動命が打ち込まれる。**

併せて major を三つ: 失敗時に Bun の開発用頁（stack・source・絶対道）が
出ておったのを素っ気ない 500 に。`serve()` が**願った繋ぎ先**を返しており
「0.0.0.0 で開いておらぬか」の見張りが己の願いを見て頷くだけであったのを、
**繋がった先**を返すよう直した。Host の検めは最初 `port: 0` の試験を弾いた
——**願った番号で検めておった**ゆえで、試験が即座に暴いた。

残りは Issue へ回す（Ctrl-C で窓が止まらぬ、輪が永遠に諦めぬ、口の見分けが
素性を問わぬ、status の死んだ枝、など）。

### 百三十八、見張りは「印」で見よ——名でも口でもなく（2026-08-29）

レビューの major が同じ一点を三方から突いた。窓の生死を

- 「viewer という名の窓があるか」
- 「curl が何か返すか」

で判じておった。**どれも他人で成り立つ。** 8787 に OpenAI の中継が座っておった
一件がその証である。配信に印（`X-Honden`）を返させ、**印でのみ**生死を判ずる

**己の内への問いが中継へ攫われる。** この機は `http_proxy` を持ち、127.0.0.1

### 百三十九、本番の正本が壊れておった——移行を書き忘れておる（2026-08-29）

実弾で `status` を叩いたら **SQLite の生の悲鳴**が出た:
`no such column: holder`。

型（`CREATE TABLE IF NOT EXISTS task`）には `holder` / `leased_at` /
`lease_until` が在るが、**`CREATE TABLE IF NOT EXISTS` は既にある表を変えぬ**。
貸与の欄を型へ足した折に `addColumn` を書き忘れており、先に建った正本
——つまり**本番**——では貸与を読む口が全て倒れておった。

`nudge.reset_count` で一度踏んだのと**同じ型**である。二度目ゆえ、訓戒でなく
機械を置いた: 貸与を知らぬ頃の形で表を建ててから migrate を通し、型が言う欄が
揃うかを数える試験（`test/store.test.ts`）。移行の一行を外すと落ちることも
確かめた。

本番の正本は写しを焼いてから直し、`status` が生き返るのを実見した。

**教訓は「型に足したら移行にも足す」ではない。** それは一度目に学んだはずで、
二度踏んだ。**型と実物を突き合わせる機械を置く**——それが二度目の学び方である。

### 百四十一、陣に印を付けた——名は世に一つではない（2026-08-29）

`multiagent` という名の陣が我らのものとは限らぬ。よその陣へ窓を接いだ上で
「撤収は `tmux kill-session -t multiagent`」と案内すれば、**他人の陣ごと
畳ませる**（敵対レビュー critical）。

立てた折に `@honden` の印（値は $ROOT）を付け、**接ぐ前に必ず確かめる**。
印が無ければ窓も芯も接がず、別の名で立てるよう促す。

同じ「名で判ずるな」の型が三つ揃った——窓の生死（口・窓名でなく印）、
芯の数え（名でなく見張る先）、陣の素性（名でなく印）。**名は当てにならぬ。
持ち物か否かは、己で付けた印でしか判らぬ。**

併せて `status` の死んだ枝を直した。`grep | awk || echo` は awk が必ず 0 で
終わるゆえ「動いておらぬ」へ辿り着けなんだ。受けてから数える形に。
Ctrl-C の物言いも直した——輪は既に抜けておったが「五度倒れた」と嘘を言うており、
止めの合図と力尽きたのを言い分けるようにした。

### 百四十四、名乗りの錨を本体へ配線した（2026-08-29・殿裁可 Issue #7）

|---|---|
| `HONDEN_AGENT_ID=shogun` で許状を切る | 「将軍のみ（そなたは ashigaru1）」 |

### 百四十六、拒みが跡を残さなんだ（2026-08-29）

D015 を据えて実測したところ、より重いことが分かった。**門は拒むが、誰が何を
試みたかがどこにも残らなんだ。** 直訴すれば刻まれるが、直訴せぬ者の跡は消える。
「秘密を読もうとした者が居た」という最も知りたい事実が、消えておった。

殿の言う「同じ経路」には**監査**も含まれる。拒みを台帳へ落とすようにした
（`guard.deny` / 誰が・どの規則を・何で叩いたか）。**許しは刻まぬ**——常道に
費えを課さぬため。拒みは稀ゆえ台帳は太らぬ。太るとすれば、それは**同じ壁を
何度も叩いておる者が居る**という報せであり、消してはならぬ signal である。

記帳に失敗しても拒みは返す。見張りの不調で門が開いては本末転倒ゆえ。


### 百四十七、叩かれた壁を数える——数でなく散らばりを見る（2026-08-29・殿の指摘）

殿の指摘——「同じのが叩かれ続けるなら、誤検知なのかも確認しないとだな」。
拒みの数を並べても、**三つを見分けられぬ**: 注入された者・心得が不明瞭な者・
そして**条そのものが広すぎる**場合。

見分けは散らばりで立つ。条は仕組みの性質ゆえ、**皆が等しく叩くならそれは
常道を捕らえておる**。一人だけが叩くなら、条ではなくその者の話である。

| 見る軸 | 注入・誤解 | 条の誤り |
|---|---|---|
| 担い手 | 一人が繰り返す | 多くの者が等しく叩く |
| 命の形 | 同じ形を何度も | 形は様々で条だけが同じ |
| 直訴の帰結 | 却下される | **通り続ける** |

三つ目が最も鋭い。**直訴が上がり手形が下り続ける条は、答えが常に諾となる
問いを毎度発しておる**に等しく、門としての意味を失うておる。ゆえに叩きの数を
待たずに疑う。これを数えるため、手形の記帳へ `rule=` を足した——無ければ
「どの条を開けたか」が後から辿れぬ。

**命の「形」で括る。** 生の命をそのまま数えると引数違いが別物に見え、
**注入の繰り返しが「様々な形」に化ける**。道具の名と副命令までで括る
（`cat /a/app.pem` と `cat /b/app.pem` は同じ形、`tmux send-keys` と
`tmux kill-pane` は別の形）。

**材料が足りねば疑いを述べぬ。** 一度や二度の拒みで条を疑えば門が萎える。

**無い時の物言いに気を配った。** 拒み 0 は良い報せに見えるが、**門が外れて
おっても 0 になる**。ゆえに「門が生きておる証ではない・生死は gate で別に
確かめよ」と添える。集めた層が自分の沈黙を健全と偽らぬように。

そして本日、**この機能を試す最中に我が身で誤検知を踏んだ**——
`rm -rf /tmp/claude-1000/denialprobe` が `.claude/settings.json` の
`rm -rf /*` に当たった。scratch を掃く正当な手が、絶対道というだけで
止められる。誤検知は絵空事ではない、という証を、作っておる当のものが出した。


### 百四十八、rm と glob を封じ、明示の道だけを通す（2026-08-29・殿命）

殿命——「事故が起きかねない rm と * の組み合わせパターンは封じて、明示的に
指定するようにして」。

**守るべきは根や家ではなく、展開そのものであった。** 事故の型はここにある:
空の変数で `rm -rf $DIR/*` が根を指す・思わぬ cwd で `rm *` が別の家を掃く——
**展開の結果は、打った本人にも見えぬ**。

これまでは根と家を列挙して守っておった。その手は**守り漏れと誤検知の両方**を
生んだ。実測すると `rm -rf /*` は門を素通りしており（D001 は glob 無しの形しか
見ておらなんだ）、一方で `.claude/settings.json` の一行が
`/tmp/…` を掃く正当な手まで止めておった。**守るべきものを守らず、
守らずともよいものを守っておった。**

二層に分けた:

- **D001（絶対域）** — 根への glob。`rm -rf /*` `rm -rf /mnt/*` `rm -rf ~/*`。手形でも通らぬ
- **D016（直訴可）** — その他あらゆる rm × glob。`rm *` `rm -f build/*` など

明示の道は通る。`rm -rf /tmp/…/probe` も `rm -f a.txt b.txt` も
`rm -rf node_modules` も素通りする——**境が glob の有無という一点で決まるゆえ、
何が通り何が止まるかを打つ前に判ずることができる。**

glob で掃きたい正当な用（build 生成物など）は直訴すればよい。稀なら手形で
足り、頻繁なら denials の帳面が「条を疑え」と言う。**条の是非を人の記憶でなく
帳面が判ずる**形になった。

`.claude/settings.json` の側も、危うい根を**明示で列挙**する形へ改めた
（18 条）。`/tmp` と `/run` は掃き場ゆえ入れぬ——掃除の正当な手を止めれば、
その条は誤検知として叩かれ続ける。

**同じ型の誤検知を、この作業の最中に二度踏んだ。** 一度は掃き場の掃除が
弾かれ、一度は**命令文の中に禁じの字面を書いただけ**で弾かれた（deny の
一覧を編む python の中に、その一覧そのものが現れたゆえ）。後者は D015 で
学んだはずの型である——**規則を書く手が、その規則に弾かれる**。
字面を変数へ閉じ込めて凌いだ。

なお honden の門は直ったが、**将軍自身の session は旧 repo の settings で
治められておる**ゆえ、切り替えまで将軍は弾かれ続ける。


### 百四十九、構文解析の門に借りる parser を決めた——brush-parser（2026-08-29）

十八で「候補の版と保守状況は建てる時に要確認」と先送りしておった問い。
合図が鳴った（継ぎ四枚）ゆえ、実測して決めた。

**十の関門を作って両者に通した**（env 前置・旗と値・heredoc・引用・道・
glob+変数・pipeline・eval・命令位置の $()・壊れた入力）。**両者とも全て通過**。
ゆえに決め手は機能ではなかった。

| | brush-parser 0.4.0 | yash-syntax 0.24.0 |
|---|---|---|
| 免許 | **MIT** | **GPL-3.0-or-later** |
| bash の網羅 | 実 bash と約 1,700 の照合試験 | POSIX 主。`((式))` を**黙って入れ子 subshell と読む** |
| AST の据わり | 語は生の文字列。引用は二段目（`word::parse`） | 引用が AST に第一級。据わりは最良 |
| 解く速さ | 1.35 µs | 4.83 µs |
| binary | 0.69 MiB | 1.31 MiB |
| 一回の費え | 1.25 ms | 1.31 ms |

**免許で決した。** honden は MIT であり、GPL を混ぜれば配る binary ごと GPL に
なる。公開している以上、これは理屈でなく制約である。

**そして技の側の決め手が、免許と同じ向きを指した。** yash は `((式))` を
入れ子の subshell として**誤りなく読む**——つまり誤りを誤りと言わずに読み違える。
`&>f` も POSIX 流に割る。`[[ ]]` と `<(...)` は型に無い。

**これは、この門を建てる理由そのものと真っ向から反する。** 黙って読み違える
parser は「解けた」と言って掟に照らす——**成功の顔をした fail-open** である。
本日一日、あらゆる層で潰してきた型がこれであった。**誤読するより、
落ちる方がよい。**

honden の配下は皆 bash で走る（claude / codex / cursor いずれも）。
`[[ ]]` も `((` も `<(...)` も**日常の往来**であって珍種ではない。
POSIX 限りの parser は、それらを routine に読み違える。

**受け入れる代**: brush の AST は語を生の文字列で持つゆえ、引用と命令置換を
見るには語ごとに `word::parse` を通す二段目が要る。**この二段目は生まれた
時から fail-closed にせよ**——`WordParseError` は「その語を飛ばす」ではなく
**拒む**こと。新しい層は fail-open として生まれる、を四度目に繰り返さぬために。

**退けた道**: conch-parser（墓・archive 済）、mvdan-sh の npm（upstream が
archive）、tree-sitter-bash（**ERROR 節点で回復する**——落ちてくれぬ parser は
fail-closed の門に使えぬ）、rable / shuck-parser（0.2.1 / 0.1.3・数ヶ月・
守りの境に据えるには若い）、sh-syntax の WASM（生きてはおるが Go の意味論を
WASM 越しに借りる形で、Rust の道が実測で足りておるゆえ採らぬ）。

**据え方**: 別 crate `core/guard`、別 binary。実測で**一回 1.25 ms**——門自身が
55 ms ゆえ 2% 程度で、WASM や in-process の細工は要らぬ。芯（`core/watch`・
依存ゼロ）には混ぜぬ。

**実測の跡**: probe は `/tmp/claude-1000/parserprobe`（両 crate + 単体 binary
三本）。cold build 12.6 秒、incremental 0.7 秒。

**なお yash で一つ実測の収穫**: 末尾の改行が無い heredoc を**誤りとして落とした**
（brush は通した）。hook から来る命令は末尾改行が無いことがあるゆえ、
どちらを採っても入力の正規化は要る、という報せである。


### 百五十、構文解析の門を建てた（一段目）——`core/guard`（2026-08-30）

合図が鳴り（継ぎ四枚）、parser も決まった（brush-parser）。建てた。

**一段目の狙いは、掟の移行ではない。** 十六条を一度に書き換えれば、通っておる
116 の試験を網にできぬ。まず**構造を渡す層**と**拒みへ倒れる筋**を据える。
掟は次段で一条ずつ移す。

#### 芯（Rust・`core/guard` → `bin/honden-parse`）

判定はせぬ。解いた構造だけを JSON で返す。**掟は TS 側に置く**——掟は人の
言葉で読めるべきで、Rust に埋めれば誰も読まなくなる。

返り方は三つ。**二段目が肝である。**

| | 意味 | 門 |
|---|---|---|
| `ok: false` | 解けなんだ | 拒む |
| `ok: true, complete: false` | 解けたが畳めぬ部分がある | **拒む** |
| `ok: true, complete: true` | 全て見えた | 掟に照らす |

「解けた」とだけ言うて中途半端な argv を渡せば、門はそれを全体と思うて照らす
——**成功の顔をした fail-open** になる。畳めなんだ物（算術・プロセス置換・
`[[ ]]`）が一つでもあれば、そう言う。

probe の写しには fail-open が二つ残っておった。両方その場で塞いだ:
語の解析失敗を `Err(_) => {}` で既定値に落としておった（＝「引用されておらぬ・
glob 無し」と**嘘をつく**）のと、畳めぬ複合命令を黙って捨てておったのと。

#### 皮（TS・`src/parse.ts`）

**解けぬ・畳めぬ・道具が無い・落ちた・返事が読めぬ——全て同じ一つの型**
（`ok: false` と理由）に畳んだ。呼ぶ側が「この場合は通してよいか」と迷う余地を
残さぬため。**迷う余地があれば、いつか誰かが通す。**

語の素性は**欠けたら真に倒す**。芯が新しい印を足して古い binary が返さぬ、
という食い違いで「印が無い＝安全」と読めば、知らぬ危うさを見逃す。

道具を実際に外して試験を回し、**落ちて焼き方を告げる**ことを確かめた
（黙って緑にならぬ）。「道具が無いから飛ばす」は、この層が塞いでおる型そのもの。

#### 実測

| | |
|---|---|
| binary | 510 KiB |
| 一回の費え | **6.6 ms**（門自身 55 ms に対し 12%） |
| 十の関門 | 全通過。引用・heredoc の中身が命令位置から外れる |

`echo "rm -rf /*"` の `rm` は `quoted` の語として現れ、命令位置に立たぬ。
`python3 <<'EOF' … EOF` の中身は `heredocs` へ落ち、argv は `python3` のみ。
**将軍が二度弾かれた形が、構造として消えた。**

#### 次段

掟を一条ずつ構造の上へ移す。D016（rm × glob）は `glob` の印で書き直せ、
D015（秘密を読む）は命令位置の argv で書き直せる。移すたびに、その条の
陽性対照が「文中の字面では当たらぬ」ことを言えるようになる。


### 百五十一、二段目——紋様の錨は、命令位置の近似にすぎなんだ（2026-08-30）

掟を構造の上へ移す段。移す前に測ったところ、**移行の動機が変わった。**
誤検知の話だと思うておったが、はるかに重いのは**取りこぼし**であった。

紋様の錨 `(?:^|[;&|]\s*)` で、絶対域の D001（`rm -rf /`）が**六つの形で
素通り**しておった:

```
ls⏎rm -rf /                改行は錨に入っておらぬ
if true; then rm -rf /     then の後は錨に入っておらぬ
x=$(rm -rf /)              置換の中は見ておらぬ
for f in a; do rm -rf /    do の後も同じ
{ rm -rf /; }              波括弧の中も同じ
while true; do rm -rf /    同上
```

**改行で継ぐだけで根を消す命が通る。** 珍しい形ではない——複数行の命を書けば
routine に出る。門は三ヶ月これを通しておった。

#### 直し方——紋様は書き換えぬ

**単純命令ひとつを一つの単位**として紋様に照らす。単位の先頭が命令位置その
ものゆえ、錨の近似が要らぬ。十六条を一条も書き換えずに、錨だけが本物になった。

二枚重ねにしてある（紋様と構造の**どちらかが止めれば止める**）。構造だけに
移せば、構造が取りこぼす形で門が緩む恐れがある。紋様を降ろすのは、構造が
本番で通ってからでよい。

命令置換の中身は**別の命**として再帰して解く（深さ二段まで）。heredoc は
**貰い手で分ける**——`python3 <<EOF` の中身は文字、`bash <<EOF` の中身は命。
構文では見分けられぬゆえ、貰い手の名簿を短く明示で持つ。

#### 一巡した——整形が構文を壊しておった

六つのうち改行の一つだけが、直しても通り続けた。因は `normalize` である。
紋様のために改行を空白へ潰す整形が、**構文の意味まで壊しておった**——
`ls⏎rm -rf /` が `ls rm -rf /`（ただの ls）に化け、根を消す命が消えて見えた。

`splitOtp` が**生の姿も返す**形にし、構造には生を、紋様には整形済みを渡す。
陽性対照つきで釘を打った（潰した方を解けば通ってしまうことも試験に書いた）。

**教訓**: 前処理は下流の層ごとに意味が違う。紋様のための整形を、構文の層へ
そのまま流してはならぬ。

#### 芯の側でも一つ塞いだ

代入語（`x=$(…)`）を解いておらなんだ。値として控えるだけで、中の置換を
拾っておらず——**代入に隠れた命が門の外を素通り**しておった。解く形に直した。

#### 実測

| | |
|---|---|
| 六つの抜け道 | **全て塞がった**（hook の実弾で確認） |
| 誤検知 | `echo rm -rf /` / `grep 'rm -rf /'` / `rm -rf .tmp/work` いずれも通る |
| 試験 | 809（うち構造の層 20・対で紋様の取りこぼしも示す） |

釘は**対で**打った。「紋様では通り、構造では止まる」を一つずつ示す——
片方だけでは「元から止まっておった」のか「構造が効いた」のか判じられぬ。


### 百五十二、出す前に実物で測った——誤検知は零（2026-08-30）

構造の門は**全エージェントの全ての命の通り道**に立つ。正当な命を拒めば仕事が
止まる。**出す前に、実物で測った。**

料は手元にあった——記録（transcript）から実際に打たれた Bash の命を抜く。
**14,131 通り**（重複を除く）。作り物の試験ではなく、本当に打たれた命である。

#### 一巡目: 38 件が拒まれた（0.3%）

内訳を見れば、大半は**我が手落ち**であった。

- **プロセス置換 `<(…)` が 17 件。** 「畳めぬ」と言うて拒んでおったが、
  `comm <(a) <(b)` も `diff <(x) <(y)` も日常の往来である。
  **畳めるものを畳まずに拒むのは、門ではなくただの障害物。** 中身を歩く形に直した。
- **`[[ … ]]` が 1 件。** 条件式は命を走らせぬ。だが中の語は展開される
  （`[[ -n $(cmd) ]]` の cmd は走る）。語だけ解いて置換を拾い、
  命令位置には入れぬ形にした。

直して二巡目: **20 件（0.1%）**。

#### 二巡目: では、その 20 件は誤検知か

**判ずるのは我らではない。bash 自身に判じさせた。**

`bash -n` に掛けたところ 13 件は bash も拒み、7 件は通った——「誤検知 0.05%」と
出た。だがその 7 件を見ると、全て heredoc であり、最小の再現はこうであった:

```
cat >> docs/issues-draft.md <<'EOF'で表示が縦割れしていた）が…
```

`<<'EOF'` の直後に空白なく続くゆえ、区切りが `EOFで表示が…` になる。
**本当に壊れた命**である。そして `bash -n` はこれを**警告に留めて 0 を返す**
（実測）。

**対照が甘かった。** 警告も落第と数えて測り直した結果:

| | |
|---|---|
| 集めた命 | 14,131 通り |
| 我らが拒む | 20（0.14%） |
| bash も拒む | **20** |
| **真の誤検知** | **零** |

#### 学び

**陽性対照そのものを疑え。** 「bash が通すなら正当」という対照を立てたが、
その bash が警告で済ませておった。対照が甘ければ、甘い結論が出る——
そして甘い結論は「誤検知 0.05%」という**もっともらしい数**の顔をして現れる。

実物で測らねば、この二巡はどちらも起きなんだ。作り物の試験では
`comm <(a) <(b)` を思いつかず、プロセス置換で 17 件を拒む門をそのまま
本番へ出しておった。**十の関門は必要だが、十では足りぬ。**


### 百五十三、卓上へ報せる——層を分けて、押せる形で（2026-08-30・殿の申し出）

殿の申し出——「ntfy よりデスクトップ通知が欲しい。ntfy もいずれ入れる。
port しつつレイヤー分けするか」。**送り口が増えるたびに「何を報せるか」を
書き直すのでは、二本目で必ずずれる。**

```
src/notify.ts          何を報せるか（純関数・送り口を知らぬ）
  └ notify/desktop.ts  Windows の対話式通知
     （notify/ntfy.ts  いずれ足す。芯は書き換えずに済む）
```

`identity.ts` の `lookup`、`parse.ts` の `Runner` と同じ流儀である。

#### 測って分かった三つ

**一、借り物も登録も要らぬ。** BurntToast のような module は入れずに済んだ
——素の COM（`Windows.UI.Notifications`）で対話式の通知が鳴る。実測。

**二、ボタンの行き先は `http://` で足りる。** 独自 protocol（`honden:`）で
受けるには registry の登録が要るが、**配信の窓が既に 8788 に立っておる**ゆえ、
そこを指せば既定の browser が開くだけで済む。COM server も要らぬ。

**三、符号化の罠。** PowerShell 5.1 は BOM の無い `.ps1` を**既定の符号系**
（この機では Shift-JIS）で読む。WSL から書いた UTF-8 の日本語は化ける
——最初の試し撃ちで実際に化けた。`-EncodedCommand`（UTF-16LE の base64）なら
ファイルも BOM も要らぬ。中身の無傷を**文字符号で**確かめた（日=26085・—=8212）
——見た目で確かめると、戻り道の化けと区別がつかぬ。

#### 意を用いた三点

**二度撃たぬ。** 撃った跡を台帳に残す。同じ裁可を毎度撃てば通知そのものが
無視されるようになる——**狼少年になれば、見張りが無いのと同じ**。

**全滅した時だけ刻まぬ。** 送り口が複数ある時、片方が落ちても届いておれば
刻む。全て落ちた時だけ刻まず、次の機会に撃ち直せるようにする。

**配下の書いた文が作りを壊さぬ。** 裁可の問いは家老や軍師が書く。XML へ
差し込む字を殺さねば `"><action …>` で**勝手なボタンを生やされる**
——押せる通知ゆえ、これは実害である。「我らが組んだ二つ以外に action が
生えぬ」を釘に打った。

#### 実弾

試験の陣に本物の裁可を立てて撃ち、殿の卓上に届いたことを確かめた
（`#2 卓上の報せは殿の目に届くか` が本文に出た）。二度目は撃たぬことも確認。

#### まだ無いもの

撃つ時機は `honden notify` を叩いた時だけである。裁可が立った瞬間に撃つか、
芯が周期で見るかは未定。ボタンで**答えられる**ようにする道もあるが、
押しただけで正本が変わる作りは危うい——browser の click 一つで書けるゆえ、
窓を開いて**そこで確かめてから書く**（見せるのは GET、書くのは POST）が筋。

### 百五十五、ntfy の送り口を建てた——公開しておるゆえ（2026-08-30）

直し、素振りの後も報せが残ることを実測し、芯の側に釘を打った。

**同じ罠は旗を消す全ての副命令に潜む。** 新しい口を足す時は、`flags` でなく
`dryRun` を見ること。

#### 試験の枷も一つ

試験が 871 に増え、`ulimit -v 2GB` では bun が落ちるようになった。4GB へ。
**落ちたのは試験ではなく枷である**——切り分けねば「試験が壊れた」と読み違える。


### 百五十六、写真一枚が、試験十九本より多くを教えた（2026-08-30）

殿の問い——「旧実装と同じような画面で見れるか」。旧環境が残しておった写真
（`images/screenshots/masked/ntfy_cmd043_progress.jpg`）を見て、**同じ形に
ならぬ**と判じた。継ぎ目の試験は十九本すべて緑でありながら、である。

写真から三つ直した。

**一、見出しを付けておった。** 旧 `ntfy.sh` は `-d "$1"` と本文だけを投げ、
端末では会話のように並んでおった。見出しを足せば一行増えて並びが崩れる。
**本文の一行目に畳む**形に改めた。

**二、符号化が誤っておった。** 「ntfy の見出しは ASCII のみ」は真だが、
やり方が percent 符号化では**化ける**。公開の ntfy.sh へ無害な試しを三通り
撃って読み返した:

| 送り方 | 端末に出る見出し |
|---|---|
| percent（我が実装） | `%E6%AE%BF%E3%81%B8` |
| **RFC 2047**（`=?UTF-8?B?…?=`） | `殿へ` |
| 無し（旧） | 無し |

正しい包み方は `encodeTitle` として残した——後日、頭で送る要が出た時のため。

**三、印が `honden` になっておった。** 旧の `outbound` は**受け手が自分の声を
弾く印**である（`ntfy_listener.sh`）。名を変えれば、いずれ受けを建てた時に
輪ができる。旧に揃えた。

#### 学び

**「何を投げるか」は測れても、「どう見えるか」は測れぬ。**

継ぎ目の試験は全て緑であった。宛先も、合鍵の組み立ても、落第の言い分も
留めてあった。だが**出来上がりの姿**——端末に何行で、どう並ぶか——には
一本も触れておらなんだ。そこを教えたのは写真一枚である。

移植で「同じ物を作った」と言えるのは、**出口を見比べた時だけ**である。
入口を揃えても、出口が違えば別の物になる。旧環境が写真を残しておったのが
幸いであった——残っておらねば、殿が端末を開くまで誰も気づかなんだ。


### 百五十七、報せる出来事を旧の四種へ揃えた（2026-08-30）

殿の指し——「旧環境の 8. Phone Notifications に色々書いてある」。読んで、
**我が実装が一種しか報せておらぬ**と分かった。

| | 旧 README が挙げる | 建てた時 | 今 |
|---|---|---|---|
| 🚨 | Action needed | 有り | 裁可待ち |
| ✅ | cmd complete — 5/5 subtasks | **無し** | 司令の完了（受け入れ条件の数つき） |
| ❌ | subtask failed — reason | **無し** | 倒れた任・品質の落第 |
| 🔥 | 3-day streak! 12/12 today | **無し** | 連続と今日の進み |

**一つでも欠ければ、殿は端末を見る習慣を失う。** 見ても半分しか載っておらぬなら、
結局は戦況を開くことになり、通知そのものが死ぬ。四種そろって初めて
「端末だけ見ておればよい」が成り立つ。

**連続は日で撃つ。数では撃たぬ。** 数が動くたびに鳴らせば一日に何度も鳴り、
煩わしさで無視される。日が変わって初めて撃つ。

#### まだ無いもの（README が挙げておるうち）

- **受け（スマホ→将軍）**。`ntfy_listener.sh` が受けて `queue/ntfy_inbox.yaml`
  へ書き、将軍を起こす。受領を自動で返す（`📱受信: {本文}`）仕掛けもある。
  殿がまだ ntfy を建てておられぬゆえ、建った後に。
- **家老が直に撃つ**という筋。旧では家老が dashboard を更新した折に
  `scripts/ntfy.sh` で直に撃ち、**将軍を通さぬ**（将軍は人との応対に専念する）。
  honden では今、`honden notify` を叩いた者が撃つ——時機の設計はこれから。
- **Frog**（その日の最も重い一つ）。saytask に欄が無い。

#### 学び

**README は仕様書である。** 実装（`ntfy.sh` 25 行）だけを読んで移し、
「同じ物を作った」と思うておった。だが 25 行が語るのは**送り方**だけで、
**何を送るか**は README にしか書かれておらなんだ。

移植で読むべきは、動く物と、それを説明した物の**両方**である。


### 百五十八、報せが鳴る道を作った——芯に乗せる（2026-08-30・殿の裁可）

建てた報せが**本番で一度も鳴っておらなんだ**。誰も `honden notify` を叩かず、
台帳の `notify.sent` は零。**層は建ったが、飾りのままであった。**

道は三つあった。出来事の起きた所で撃つ（あ）・芯が拾って撃つ（い）・
窓として常駐させる（う）。殿は**（い）を裁可**。

#### なぜ（い）か

honden には旧に無い利がある——**芯（core/watch）が既に正本の動きを見張って
おる**。正本が動けば芯が起き、`honden nudge` を叩く。ここに乗せれば:

- **口が一つで済む。** 出来事ごとに撃つ口を散らせば、新しい出来事を足すたびに
  撃ち忘れの筋が生まれる
- **撃ち漏らしが無い。** 正本が動けば必ず通る道である

#### 意を用いた三点

**合図が本務。報せの躓きで合図を止めぬ。** 掴んで黙る——掴まねば、通知の
道具が無い機で**配下が起こされなくなる**。本末転倒である。

**素振りでは撃たぬ。** 百五十五で踏んだ罠を繰り返さぬ。

**切れる道を残す。** `notify.enabled: false` で黙る。煩わしくて切れねば、
いずれ通知ごと無視されるようになる——切れることが、鳴り続けるための条件である。

#### 実測

裁可を立てた 5 秒後、誰も叩かずに三件が撃たれた（`notify.sent (decision:6)`
ほか）。切れば零、戻せば一——陽性対照つき。

**費えは 1 ms。** 当初 133 ms と読んで慌てたが、切り分ければ合図そのものが
261 ms で、報せの分は 1 ms であった。撃つ物が無ければ SQL を数本引くだけで、
外の道具（PowerShell / curl）は**撃つ物がある時にしか起きぬ**ゆえ。

**差の測り方を誤れば、無い問題を直しにかかる。** 片方だけ測って「倍になった」と
読んだのが我が誤りで、両方測れば一目であった。


### 百五十九、Issue #8 の残り四件を塞いだ（2026-08-30）

いずれも軽いが、放てば「見張りが嘘をつく」型へ育つ筋であった。

**一、`exec bash` は構えを渡さぬ。** 根の入口が `set -euo pipefail` を敷いても
中では errexit が off——実測で確かめた（`false` の後も続き、0 で終わる）。
**入口に頼れば、半端な陣でも 0 で終わる。** 中の書が己で構えを取る形にした。
ただし errexit は敷かぬ——この書は「既にある」を warn で流して進む作りゆえ、
-e を入れると途中で黙って止まる。pipefail と nounset を取り、要所は die で落とす。

**二、道の単引用符。** 窓を立てる命を単引用符で括っており、道に `'` があれば
破れた。`printf %q` で包む——shell が読み戻せる形にしてくれる。

**三、外への断りが誰も読まぬ所に出ておった。** 窓の中（tmux の別窓）では
出陣を打った者の目に入らぬ。入口へ移した。

移す際、試験が**正しい欠けを突いた**——既に応えておる時は早々に返り、断りへ
届かなんだ。**危ういのは「今開いたか」ではなく「開いておるか」**であり、
二度目に黙れば忘れられる。ゆえに立てる時だけでなく、既に立っておる時も言う。

**四、冷えた土地での偽の「応えぬ」。** 一度きり 2 秒の下見では、冷えた
/mnt/c で起き上がりに間に合わぬ。間を置いて五度問う（試験では待たぬ）。
