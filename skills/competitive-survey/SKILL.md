# /competitive-survey — 競合比較調査スキル

## 出自

同じ型の調査を繰り返すたび、同じ失敗をした。軸がずれる、紹介の受け売りになる、
自分側との対比が抜ける、**測ったものと主張したいことが違う**。

この手順は、その五つを訓戒ではなく所作へ落としたものである。
読んで気をつけるのではなく、**書かねば次へ進めない欄**として置いてある。

とりわけ Step 6（主張と測定の一致）が本体になる。見出しの数、grep の一致数、
単一部品の値——**測りやすいものを測って、測りたかったものを測った気になる**のが、
繰り返した失敗の中心であった。

## North Star

**「他所はどうしておるか」を、後から検算できる形で出すこと。**

紹介記事を作るのではない。読者が、何を移すか、なぜ移さないか、次に何を確かめるかを決められる材料を出す。

## When to Use

- 複数の道具から採用候補を選ぶ時
- 外部の機構を自分たちへ移す価値と重さを比べる時
- 設計判断を三つ以上の外部事例で裏取りする時
- 競合との機能差を、自分たちの実装を含めて検算可能にしたい時

Do NOT use for:

- 単一ツールの API や使い方を調べるだけ → Context7 または公式リファレンスを使う
- 調査を伴わない実装・設計相談 → 担当の設計・実装フローを使う
- 一次資料のないクローズド製品だけを対象にする → 対象から外した理由を記録して終了する
- 対象が二つ以下、または出典不要の発想出し

## 必須の前提

1. 対象を三つ以上挙げる。
2. Web 検索と一次資料本文の取得ができる道具を用意する。検索機能のない CLI では着手せず、使えない道具と不足能力を報告する。
3. 自分側の実物（コード、設定、実行結果、運用データのいずれか）を読めることを確認する。
4. 調査日、対象範囲、採否を決めたい問いを一文で固定する。

## Instructions

### Step 1: 採否を決めたい問いと対象を固定する

最初に次を一行ずつ書く。

- 決めたいこと: 調査後に可否または優先順位を決められる形の問い
- 自分側: 比較対象となる現行の製品、リポジトリ、手順
- 候補: 三つ以上
- 調査範囲: 比較する版、日付、機能範囲

候補ごとの紹介を書き始めてはならない。先に同じ問いへ答えられる対象かを揃える。

### Step 2: 一次資料ゲートを通す

比較表より先に「証拠台帳」を作る。対象ごとに公式 documentation、仕様、論文、公式 repository の URL、確認日、そこから確認する事実を書く。

- 一次資料本文を取得し、主張を支える箇所まで読む。検索結果の要約文だけを根拠にしない。
- 二次資料しか見つからない対象は、比較対象から外すか、証拠水準を「二次のみ」に落として結論から分離する。
- URL があっても本文を確認できなければ「未確認」とする。
- 対象を外した場合も、対象名、探した範囲、外した理由を「分からなかったこと」へ残す。

### Step 3: 比較軸を立て、途中で固定する

今回の採否判断に必要な軸を三つ以上立て、各軸の直後に「この軸が採否へ効く理由」を一文で書く。以前の調査の軸を無条件に流用しない。

軸を宣言した後は、全対象を同じ軸で埋める。途中で新しい軸が必要になった場合は全対象を遡って埋め直すか、その軸を今回の不明点へ送る。都合のよい対象だけに軸を足さない。

### Step 4: 自分側の現況を実物で測る

各軸について、文書を入口にしてもよいが、結論の根拠は実物で取り直す。

1. 文書から該当しそうな実装・設定・データの場所を特定する。
2. コード検索、設定値の読み取り、実行、テスト、データ照会のうち適切な方法を実行する。
3. 観測したコマンドまたは操作、対象 path と行、結果を「自分側の実査台帳」に記録する。
4. 文書と実物が食い違えば実物を現況とし、食い違い自体を不明点または必要作業にする。

**全軸に「自分側はいまどうしているか」と実物の出典が入るまで対比を完成扱いにしない。**

### Step 5: 軸ごとの表と移植判定を作る

対象ごとの箇条書きではなく、軸ごとに同じ列を持つ表を作る。各軸には次を必ず置く。

| 対象 | 機構・観測事実 | 一次資料 | 証拠水準 |
|---|---|---|---|
| 候補 A | 事実 | URL または path:line | 一次確認済み / 二次のみ / 未確認 |
| 自分側 | 現況 | 実査した path:line または操作 | 実物確認済み |

表の後に、移植可否、必要作業、重さ、期待効果、見送り理由を書く。

### Step 6: 結論の直前に「主張と測定の一致」を検める

結論ごとに、次の一行を先に書く。

`主張: ... / 測ったもの: ... / 同じものか: yes|no / no の場合: 中身を測り直す、または主張を測定範囲へ狭める`

見出し名、件数、grep の一致数、単一部品の値だけから、中身、利用実態、合成結果を断定してはならない。`同じものか: no` のまま結論へ進まず、実体を読むか「名称上」「検索範囲では」など測れた範囲まで主張を狭める。

### Step 7: 「無い」の探索範囲を記録する

「同等物なし」「対応していない」「使われていない」と書くたび、直後に次を添える。

`不在主張の範囲: 調べた資料・path / 検索語または確認方法 / 確認日 / 表現: この範囲では見つからなかった`

検索範囲が有限なら、絶対的な「存在しない」へ言い換えない。網羅性を証明できた場合だけ、その証明方法を添えて強い不在主張を許す。

### Step 8: 優先順位を決める

候補を、少なくとも「期待効果」「必要作業」「導入リスク」「証拠の強さ」で並べる。点数を使う場合は尺度を先に定義し、点数だけで決めず理由を一文で添える。

自分側が優れている点も、Step 6 と Step 7 の検めを通す。候補側を調べた範囲に無かっただけなら「調査範囲では見つからなかった」と書く。

### Step 9: 不明を独立して残す

最後に必ず「分からなかったこと」を置く。空欄は禁止する。

- 取得できなかった一次資料
- 実物まで確かめられなかった自分側の現況
- 版、運用条件、性能、費用など比較できなかった軸
- 不在主張の探索範囲外

不明が見つからなかった場合は「不明なし」で済ませず、題材が易しすぎた可能性と、追加すると不明が露出しうる条件を書く。

## 出力フォーマット

1. 調査目的、日付、範囲
2. 調査対象と各々の一次資料 URL（証拠台帳）
3. 軸を選んだ理由
4. 軸ごとの表（候補 × 機構）
5. 軸ごとの「自分側はいまどうしているか」——実物の出典つき
6. 軸ごとの移植判定（可否・必要作業・重さ）
7. 自分側が優れている点
8. 移植候補の優先順位表
9. 主張と測定の一致台帳、不在主張の範囲台帳
10. 分からなかったこと

## 完了ゲート

- 対象が三つ以上あり、各々の一次資料本文を確認した
- 全軸に自分側の現況と実物の出典がある
- 結論ごとに主張と測定の一致を検めた
- 不在主張を「調べた範囲では見つからなかった」として探索範囲つきで記録した
- 二次資料だけの主張を一次確認済みの事実と混ぜていない
- 移植候補を優先順位つきで並べた
- 「分からなかったこと」が具体的に書かれている

一つでも満たさなければ、成果物に漏れとして明記し、完了とは報告しない。
