# /honden-review — コードレビュースキル

> **これは派生物である。** Apache-2.0 の三つの成果（gemini-cli-extensions/
> code-review・anthropics/claude-plugins-official・openai/codex）から
> 指摘を絞る規則を借り、こちらの重大度と出力の形を足したものである。
>
> **手を入れてよい。** 追うべき上流は無く、これはこちらで育てるものである。
> ただし **honden 自体は MIT だが、このディレクトリは Apache-2.0** ——
> 変えたら、隣の `NOTICE.md` の「こちらのもの」へ書き足すこと（Apache-2.0 §4.2）。
>
> 借りた所と足した所の別、出所の版、免許の全文は `NOTICE.md` と `LICENSE` にある。

## North Star

**見落としてはならない問題を確実に見つけ、開発者が即行動できる指摘を出すこと。**
スタイルの好みや議論の余地がある設計判断ではなく、バグ・セキュリティ欠陥・明確な設計ミスに集中する。

## When to Use

- `PR #N レビューして` `コードレビューして` `/review 42` と言われた時
- セキュリティ・認証・トークン処理を含む変更を確認したい時
- ロジックの正確性・dead code・API 設計の一貫性をチェックしたい時

Do NOT use for:
- rustfmt / eslint / prettier の自動修正 → 各プロジェクトの lint スキルを使う
- テスト実行 → CI
- アーキテクチャの大方針相談 → 軍師へ
- **指摘を task へ残す** → 本スキルの**後に** `honden-review-to-task` を走らせる

## 重大度定義

| バッジ | レベル | 基準 |
|-------|-------|------|
| 💥 Critical | DBマイグレーション欠落・認証が完全に存在しない・データ破壊リスク | 即修正必須（マージ禁止） |
| 🚨 High | セキュリティ脆弱性・認証バイパス・ACL欠落 | 即修正必須 |
| 🔴 Medium | ロジックバグ・矛盾した設計・本番で問題が出うるコード・ストリーム早期中断欠落 | 修正推奨 |
| 🟡 Low-Medium | 将来の混乱・誤解を招く設計・不完全な実装 | 改善推奨 |
| 🔵 Low | Dead code・テスト欠落・ドキュメント不足・軽微な設計の不一致・監査ログの欠如 | 任意改善 |
| ✅ 良い点 | 正しく実装された重要な箇所 | 列挙して明示 |

### 🔵 Low の範囲

🔵 は **表に挙がっている「バグではないもの」だけ**に使う（dead code・テスト欠落・
ドキュメント不足・軽微な設計の不一致・監査ログの欠如）。

**挙動の欠陥を 🔵 に入れない。** 誤った結果を返す・入力を黙って捨てる・機構が黙って
無効化される・失敗経路が握り潰される、はいずれも 🔵 から外し、上の表の各行に
照らして重大度を決める。

「復旧できる」「発生頻度が低い」「自然に直る」は、実バグを 🔵 に落とす理由にならない。

## Instructions

### Step 1: PR/MR 情報を取得する

引数があればその番号を使う。なければ利用可能なツールで候補を出す。

**ホスティングサービスに応じて適切なコマンド・API を使え。** `gh` は GitHub の例に過ぎない。

| サービス | CLIコマンド例 |
|---------|--------------|
| GitHub | `gh pr view <N>` / `gh pr diff <N>` |
| GitLab | `glab mr view <N>` / `glab mr diff <N>` |
| Forgejo / Gitea | `tea pr view <N>` または REST API (`/api/v1/repos/{owner}/{repo}/pulls/{N}`) |
| その他 | `git fetch origin pull/<N>/head && git diff main...FETCH_HEAD` でローカル diff を取得 |

**取得すべき情報:**
- PR/MR のタイトル・本文（変更意図の把握に必須）
- diff（主な分析対象）
- 変更ファイル一覧

diff が大きい場合（>500行）は変更ファイル一覧を先に確認し、Step 2 の優先順で読む。

CLI が使えない・認証がない場合はユーザーに確認を求めてレビューを進めるな。

### Step 2: 変更意図を把握する

diff と PR 本文から **この PR が何を達成しようとしているか** を 1〜2 文で把握する。
この意図を念頭に置いてから Step 3 に進む（問題を探す前に「なぜこう書いたか」を理解する）。

優先読み順:
1. 認証・認可・トークン・暗号化を扱うファイル
2. DB 操作・データ変更を伴うファイル
3. API ハンドラ・ルーター
4. ユーティリティ・共通モジュール
5. テストコード（アプリケーションコードを読んだ後）

### Step 3: 変更コードを精読する

**対象は diff の `+`/`-` 行のみ。変更されていない行（コンテキスト行）に pre-existing な問題があっても指摘しない。**

diff の各ファイルについて以下の観点でチェックする:

**セキュリティ（最優先）**
- 認証・認可の欠落または過剰（二重チェックの矛盾含む）
- シークレット・APIキーの検証タイミング（起動時 vs リクエスト時）
- タイミング攻撃（ハッシュ比較は constant-time か）
- SQL インジェクション・XSS・パストラバーサル
- トークン・セッションの生成・失効・スコープ制御
- **ACL 一貫性**: 新エンドポイントを追加した場合、list/get/create/update/delete の全 CRUD に認可が適用されているか。特定エンドポイントのみ保護されて他が素通しになっていないか

**正確性**
- 矛盾したロジック（ensure_X と direct check が食い違う等）
- 戻り値・エラーの捨て捨て (`_` で無視）
- フィールドが更新されないまま残っている（last_used_at 等）
- Dead code / 呼び出されない関数・未使用フィールド
- **ストリーム早期中断**: ストリーム処理でクォータ超過・サイズ制限に達した場合、即座に中断してストレージへの書き込みを止めているか。超過後も書き込みを続けて後でエラーを返すパターンは 🔴 Medium
- **DBマイグレーション**: 新しいエンティティ・テーブル・カラムを追加した場合、対応するマイグレーションファイルが PR に含まれているか。欠落は 🔴 Critical

**コード品質**
- 関数シグネチャと実際の使われ方が乖離している
- エラーが起動時に露見せず最初のリクエストで初めて失敗する
- 命名と実装の乖離（関数名が示す動作と本体が異なる）
- **テストカバレッジ**: コアロジックにユニットテストが存在するか。結合テストのみで単体テストが皆無の場合は 🔵 Low で指摘する
- **ドキュメントカバレッジ**: 公開 API・関数の docstring 充足率が著しく低い場合は 🔵 Low で指摘する（目安: 主要な public 関数の 60% 未満）

### Step 4: 総合判定を決定する

| 判定 | 基準 |
|------|------|
| `REQUEST CHANGES` | 💥 Critical が 1 件以上（DBマイグレーション欠落・認証完全不在等）、または 🚨 High が 1 件以上、または 🔴 Medium が複数で設計として問題がある |
| `APPROVE with Comments` | 🔴 Medium 以下のみ、マージ可能だが改善余地あり |
| `APPROVE` | 指摘なし、または ✅ のみ |

### Step 5: 以下のフォーマットで出力する

```
PR #N コードレビュー

総合判定: [判定]

[2〜4文の総括。何が良くて何が気になるかを率直に書く。]

---
:boom: / :rotating_light: / :red_circle: [Critical/High/Medium]: [指摘タイトル（簡潔に）]

[ファイル名:関数名 または ファイル名:行番号]:
[問題のあるコードスニペット（10行以内。前後の文脈を含む）]
[説明: なぜ問題か、何が起きうるか]
→ [具体的な対処法]

---
:yellow_circle: [Low-Medium]: [指摘タイトル]

[場所]:
[コードスニペット（あれば）]
[説明]
→ [対処法]

---
:blue_circle: [Low]: [指摘タイトル]

[場所]:
[コードスニペット（あれば）]
[説明]
→ [対処法]

（指摘が続く場合は同様に繰り返す）

---
:white_check_mark: 良い点

- [良い点 1]
- [良い点 2]
（良い実装が見当たらない場合は「特になし」）

---
:white_check_mark: PR 内で既修正

（レビュー中に気になったが、この PR 内で既に修正・対応済みの事項。あれば列挙。なければ「なし」）
- [既修正事項 1]

---
:notepad_spiral: 仕様による意図的設計

（一見問題に見えるが、仕様・設計判断によるもの。あれば列挙。なければ「なし」）
- [設計判断 1]: [なぜ意図的か]
```

## 出力ルール

- **コードスニペット**: 問題箇所が明確になる最小限のコードを引用する。10行超は省略する
- **→ 推奨**: 具体的な修正内容を記す。「〜するか〜するか判断せよ」など二択を示してよい。「確認せよ」「検討せよ」「検証せよ」など検証系の曖昧な指示は禁止 — どう直すかを書く
- **良い点**: セキュリティ上重要な正実装は必ず挙げる。レビュアーがどこを信頼してよいか分かる
- **指摘の順序**: 💥 Critical → 🚨 High → 🔴 Medium → 🟡 Low-Medium → 🔵 Low の順。同レベル内は影響の大きい順
- **言語**: 日本語で出力する。ペルソナ由来の口調は使用しないこと
- **スニペット内コメント**: 日本語で補足コメントを追加してよい（`// ←`等）
- **指摘0件でも良い点0件でも**: それぞれ「指摘なし」「特になし」と明記する。省略禁止
- **PR 内で既修正 / 仕様による意図的設計セクション**: 該当がなければ「なし」と明記する。省略禁止
- **Low バッジは 🔵（青丸）**: 🟡 を Low に使わない。🟡 は Low-Medium のみ
- **確信度が低い指摘は出さない**: 「問題かもしれない」「気になる」レベルは除外する。確信度 ≥ 80% の指摘のみ出力する

## 指摘しないもの（偽陽性フィルタ）

以下は **指摘対象外**。誤って指摘した場合はレビューの信頼性が下がる。

| 除外対象 | 理由 |
|----------|------|
| `+`/`-` 行以外の pre-existing な問題 | 今回の変更と無関係。スコープ外 |
| lint / 型エラー / フォーマット | CI が検出する。手動指摘は重複ノイズ |
| nitpick（命名の好み・スタイル議論） | 議論の余地がある設計判断は対象外 |
| コードコメントで意図的に無視されている問題 | `// intentional`, `// by design` 等の説明がある箇所 |
| 前回のレビューコメントで既に指摘済みの問題 | PR の Conversation タブを確認し、未解決でないなら除外 |
| 変更されていないファイルの問題 | diff に含まれない箇所は対象外 |

## 注意

- diff が取得できない（private repo、CLI 未認証等）場合は明示してユーザーに確認する。`gh` が使えなくても `glab`/`tea`/`git diff` で代替できることが多い
- GitHub・GitLab・Forgejo・Gitea いずれでも動作するよう、特定 CLI に依存しない汎用手順を優先する
- PR/MR の説明文（body）も読み、変更の意図を把握した上でレビューする
- 既存コードのバグ（今回の変更と無関係）は指摘しない（スコープ外）
- 議論の余地がある設計判断（パフォーマンスの最適化方針等）は指摘せず、代わりに本文内で軽く触れる程度にとどめる
