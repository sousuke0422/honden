# memo — 起票前の構想

まだ Issue になっていない考えを置く。
一件につき一枚。

## 何のための物か

決める前の段である。
「こういう物が要るのではないか」と思いついてから、Issue として起票するまでの間、考えは行き場を失う。
会話の中に置けばセッションとともに消え、決めたことの置き場（`docs/decisions.md`）に書くにはまだ決まっていない。

ここはその間を受け持つ。

読み手は差配の層（殿・将軍・軍師）である。
足軽は読まない。足軽が読むのは `context/` の案件ごとの覚書で、あちらは「働くのに要る最小限」を置く場所である。

## 一枚の頭に必ず書く四つ

- **状態**：構想 / 保留 / 起票済 / 破棄
- **決まっていない一点**：何が決まればこれは進むのか
- **次に確かめること**
- **行き先**：どのリポジトリの Issue になるか

四つのうち最も大事なのは二番目である。
数か月後に読む者が、最初の十行で「何を決めればよいか」を掴めること。
それが無い枚は、ただ長い文になる。

## 出口を必ず持たせる

**起票したら、中身は Issue が正となる。**
枚は道標まで縮める。二つの場所に同じ内容があると、どちらが正か分からなくなる。

**建てないと決めたときも出口である。**
破棄の理由を残して閉じる。「やらないと決めた」も結論であり、同じ話が半年後にまた出てきたときに効く。

出口を定めずに置くと、実装が終わった後も原寸のまま残り続ける。
前身の環境では設計書が三つの場所に散り、合わせて 2,200 行が縮まないまま積もった。
同じ轍を踏まないために、置き場は `memo/` ひとつに限る。

## git には載せない

このリポジトリは公開で、`.gitignore` は白名簿式である。
`memo/` はその名簿に入れていない。README だけが載る。

理由は、ここが声に出して考える場所だからである。
workspace の名も、客先のリポジトリも、まだ形にならない疑いも書けなければ、置き場として役に立たない。
最初の一文字から公開であれば、書く者は読み手に向けて書き始める。

布陣の中では git は要らない。
家老も軍師も足軽も同じファイルシステムを見ている。
「追跡されている」ことと「読める」ことは別である。
公開が要るのは出口だけで、起票された Issue がその公開された姿になる。

代償として、履歴も控えも残らない。
機械が飛べば memo も飛ぶ。

## 後から公開してよい

書いてみて他所にも役立つと判じた枚は、`context/task.example.md` と同じ流儀で `.example` を付けて載せてよい。
そのときは workspace の名などを伏せる。
